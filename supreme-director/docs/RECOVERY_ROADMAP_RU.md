# Маршрут восстановления 180 задач

**Это план исполнения, не акт выполнения.** Цель — перевести работу от локальной реконструкции к реальным инженерным пакетам без подмены оригинальных систем.

## Волна 0: подтверждение корня проекта

**Блокер:** не подтверждены исходные архивы M180/M181 и точные Git SHA для шести реальных продуктов.

1. Отыскать оба оригинальных архива/коммита, проверить SHA-256, независимые копии, манифест.
2. Идентифицировать canonical upstream для TITAN, NEXUS, COMMERCE, EXPERIENCE, GENESIS, ORBITAL.
3. Проверить branch protection, права записи, lockfiles, схемы, лицензии, секреты, CODEOWNERS.
4. Записать в Issue #1–#6 маппинг `task ID -> repo -> commit -> owner -> tests`.

**Выход:** каждый источник проверен, есть независимая восстанавливаемая точка и граница ownership. Пока этого нет, нельзя автоматически объединять код в реальные системы.

## Волна 1: безопасность и контракты

- Авторизация, tenant isolation, RLS/RBAC, секреты, policy engine, idempotency.
- Изолированные тестовые среды и rollback.
- Негативные тесты, тесты восстановления, совместимость версионированных контрактов.
- Применять только к подтверждённым upstream, без внешних действий.

## Волна 2: интеграция продуктовых модулей

- Пакеты P1 по DAG из `M187_DEPENDENCY_WAVES.json`.
- Тестирование на настоящих компонентах, а не подставных заглушках.
- Для каждой границы: интерфейс, владелец, схема, error handling, контроль миграций.

## Волна 3: реальная проверка E2E

- Сценарии клиента, оператора и интеграций между сервисами.
- Контроль производительности, восстановление после отказа, отчёт проверяющего.
- Графические и мобильные сценарии — в настоящем браузере и на целевых устройствах.

## Волна 4: аудит и решение о выпуске

- P2 расширения без нарушения устойчивости.
- Полный пакет исходников/инсталлятор, лицензии, документация, подписанные артефакты.
- Выпуск только после отдельного решения владельца, security review и независимой приёмки.

## Контракт приёмки отдельной задачи

`VERIFIED` требует конкретного кода и Git SHA; unit + integration + negative/security + E2E по применимости; логи, дифф, rollback, проверенные контракты; независимую подпись проверяющего. Ссылки на PDF, презентацию или красивый интерфейс недостаточно. Пометка в браузере `READY_FOR_REVIEW` — это лишь запрос на аудит.
