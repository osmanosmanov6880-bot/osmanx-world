# OSGARD SUPREME DIRECTOR — Wave 12

Дата: 6 ноября 2026 года. Разработка в `recovery/supreme-director-m187-20261104`, Draft PR #7. `main` и production без изменений.

## Обнаруженный дефект

Миграция `LocalModelEditor.add_field` в Wave 7–11 выбирала только записи с `deleted=0`. В результате добавление **обязательного** поля с typed default изменяло активные записи, но не изменяло уже удалённые (архивные) строки. При этом `LocalProjectRecovery` при экспорте проверяет каждую строку, включая удалённые, против текущей схемы. Старый tombstone без нового обязательного поля мог привести к отказу **всего** архивного снимка.

Существенно: этот случай не был ранее подтверждён CI, поэтому код был потенциально несовместим с собственным восстановлением.

## Блок 1 — атомарная миграция активных и удалённых строк

- `model_editor.py` выбирает до 501 всех записей независимо от `deleted` и отклоняет изменения при превышении лимита 500.
- Для нового `required=true` поля при наличии **любой** активной или удалённой записи требуется корректный типизированный default.
- При заданном default обновляются все выбранные записи, пересчитываются SHA-256 и row version.
- Для каждого UPDATE версия и **флаг удаления** проверяются в условии CAS; tombstone остаётся удалённым, а ссылка из него не превращается в активную.
- Сохранение новой схемы и миграция данных выполняются одной `BEGIN IMMEDIATE` транзакцией.
- При отказе по типу, лимиту, конфликту или повреждению любая частичная мутация откатывается.

## Блок 2 — более строгое испытание восстановления

`recovery_drill.py` создаёт изолированную SQLite Online Backup копию и перед восстановлением запоминает SHA-256 содержимого 12 классов проектных таблиц:

`draft_projects`, `draft_revisions`, `builder_rows`, `builder_links`, `builder_idempotency`, `app_memberships`, `app_membership_events`, `app_workflows`, `app_workflow_runs`, `builder_model_migrations`, `builder_reference_remaps`, `builder_page_restores`.

После восстановления в новый проект сравниваются все 12 состояний исходного проекта, а не только строки и ссылки. Теперь нежелательная мутация исходных workflows/идемпотентности в копии приводит к FAIL. SQLite backup connection гарантированно закрывается, чтобы не оставлять блокировки файлов.

В публичную диагностическую сводку попадает только число проверенных таблиц, число записей и контрольный хеш; пользовательские данные и SQL содержимое не возвращаются.

## Блок 3 — отрицательные тесты

`tests/test_wave12_tombstone_restore.py` содержит 11 тестов:
- обязательное поле + живая и удалённая запись;
- обязательное поле + только удалённые записи без default (отказ);
- необязательное поле с/без default;
- ошибка типа и полный откат;
- лимит в 500 строк, включая tombstones;
- архивная запись со ссылкой без активного `builder_links`;
- внедрение незапланированного изменения source-workflows в тестовой копии;
- аналогичная мутация таблицы идемпотентности;
- отсутствие чувствительных полей в техническом отчёте;
- реальный синтетический archived сценарий.

Это авторские регрессии, а **не** независимое тестирование.

## Блок 4 — воспроизводимое CLI-испытание и GitHub CI

В `recovery_drill.py` доступны два полностью синтетических режима:
```bash
export PYTHONPATH="$PWD/supreme-director/campaign180"
python -m campaign180.recovery_drill demo
python -m campaign180.recovery_drill archived
python -m unittest discover -s supreme-director/campaign180/tests -p 'test_*.py' -v
```

Режим `demo` проверяет две активные записи и одну связь. Режим `archived` дополнительно создаёт tombstone, выполняет typed migration, подтверждает сохранность флага удаления и импортирует новую копию из 3 строк и 1 ссылки.

Оба сценария подключены к GitHub Actions `supreme-director-campaign180.yml`. Пока GitHub runner не назначен и актуальные jobs не завершились, **PASS не подтверждён**. Отсутствие подтверждённой приёмки нельзя заменять отчётом о написанных тестах.
