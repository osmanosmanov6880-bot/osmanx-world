# OSGARD — мастер-план после M185 (крупные интеграционные блоки)

Дата: 28 октября 2026. Цель — пройти путь от **локального управляющего инструмента** к международной продуктовой платформе. Это последовательный план исполнения с проверяемыми условиями выхода, а не утверждение, что система стала лучшей в мире.

## Фактическая исходная точка

- M184: автономная SQLite-панель управления предложенными задачами и конфликтами, 262 локальных теста по предыдущей поставке.
- M185: независимые локальные review cases, регистрация файлов по SHA-256, Ed25519-подпись внешним ключом, отказ от саморевью, подмены файла и повторного использования подписи; 0 product acceptance.
- Программа M182 содержит **предлагаемые** 180 задач, 174 локальных ребра, 28 placeholders конфликтов (17 P0/11 P1), 9 placeholders контрактов. Оригинальная история M180/M181 с заявленными 294 зависимостями и фактическими путями конфликтов здесь недоступна. Смешивать эти числа запрещено.
- Предыдущий M181 заявлял 176 локальных тестов; в M185 они не перепроверялись из его исходников. Локальные тесты M184/M185 не являются product E2E.

## A — M185. Подписываемые доказательства и рабочий кабинет

**Реализация:** `osgard_m185` + `dashboard/m185`. Местные файлы добавляются только по безопасному относительному пути и известному SHA-256; создание заявки фиксирует ссылку на запись; независимый рецензент подписывает канонический JSON своим Ed25519-ключом вне сервера. Сервер проверяет подпись, оригинальные байты, статус, привязку к заявке и запрет саморевью; повторное голосование невозможно. Все операции видны в аудит-журнале. Нет операции `production approve`.

**Exit gate:** исходники, отрицательные тесты, HTTP/E2E на локальных синтетических данных, Chromium 1440/390/320, повторяемая сборка. **Инженерный локальный результат** — не общая production-приёмка.

## B — M186. Каноническая цепочка шести продуктов

1. Получить **оригинальный** M181 ZIP и проверить SHA `c6d0ff3ff9caa435e6928244ab70ecee8156747306ac3174faca82702be2969a` на оригинальных байтах, а не на скопированном текстовом описании.
2. Для TITAN/KRAKEN, NEXUS/ÆTHERION, COMMERCE, HUMAN EXPERIENCE, GENESIS MEDIA, ORBITAL получить owner-approved URL, branch и 40-значный commit SHA, роль CODEOWNER и сведения о лицензиях; зафиксировать origin от upstream, не назначать владельца по похожему имени GitHub-репозитория.
3. Перестроить канонический DAG 180 задач / 294 зависимости; сравнить с предложенным 174-рёберным планом. Отметить изменения без удаления истории. Не объединять историю M182–M185 с реальным продуктовым Git, если происхождение не установлено.
4. Лишь после подтверждения исходников создать реальные карточки 28 конфликтов с обеими версиями файла, SHA-256, ревью, тестами и независимыми reviewer-keys.

**Exit gate:** 6/6 доказанных источников, 28/28 реальных карточек конфликтов, отображение реального DAG и подтверждение лицензий; до этого `BLOCKED_CANONICAL_SOURCE`.

## C — M187. Реальная межпродуктовая интеграция

1. По каждому из девяти **настоящих** API-контрактов закрепить producer/consumer, schema, API version, request/response examples, authentication, idempotency, error taxonomy, timeout/retry, privacy classification.
2. Поднять staging из канонических источников, выполнить contract + consumer-driven + negative tests; без заглушек на итоговом релизном gate.
3. Создать первую настоящую вертикальную пользовательскую цепочку (авторизация → запрос → обработка в нескольких продуктах → результат → обратная связь → история). Важно: результат должен быть полезен пользователю, а не просто отображаться в панели статуса.

**Exit gate:** 9/9 актуальных контрактов PASS в staging на точно закреплённых SHA, один полностью работающий cross-product сценарий, 0 критических нерасследованных дефектов.

## D — M188. Безопасность и операционная зрелость

IAM + OIDC/SSO + MFA; реальная tenant isolation; ролевой доступ; секреты в KMS; production-ready deployment with TLS; vulnerability/SBOM/license scans; threat modeling и независимый pentest; disaster recovery с реальным вторым хостом; испытанные бэкапы и rollback; SLO, error budgets и on-call. Нынешний локальный `http.server` запрещено публиковать в интернете.

**Exit gate:** независимая безопасность, измеренные RTO/RPO, 2-host failover, реальные нагрузочные профили и аудит-лог вне хоста, без P0/P1 security blockers.

## E — M189. Премиальный продукт и UX, а не оформление отчёта

Полноценный design system, RU/EN локализация, WCAG 2.2 AA-проверки с assistive technology и людьми, реальные устройства, performance budgets по user journey; надёжная обработка ошибок; явная подписка на данные/удаление; onboarding, рабочий цикл и self-service support.

**Exit gate:** реальные наблюдаемые пользовательские сценарии; accessibility report; измеренные latency p50/p95/p99, successful task rate, completion time, UX error rate.

## F — M190. Рынок и коммерческая жизнеспособность

Выбрать **конкретный сегмент** и одну высокоценную задачу. Проверить конкурентов и willingness to pay, провести 10–20 структурированных интервью и pilot cohort с разрешёнными данными; считать activation, weekly retention, repeated task success, cost-to-serve, margin и отток. Сначала предоставить доказанную ценность небольшой группе, затем расширять платформу.

**Exit gate:** заранее утверждённые количественные цели и подтверждённый спрос; негативные результаты не скрывать.

## G — M191. Внешняя приёмка, staged launch и отдельное GO

Независимые ревьюеры проверяют исходники, CI, криптографические доказательства, реальные миграции и recovery drill, privacy/security/accessibility. Все задачи принимаются отдельно и по исходным ID; local PASS не конвертируется автоматически в production. Только явный подписанный owner-GO открывает staged deployment. Установка canary, feature flags, telemetry и проверенный rollback.

**Exit gate:** release audit ledger; gate status ACCEPTED на подтверждённых задачах, live monitoring, воспроизводимая сборка и rollback; иначе NO-GO.

## H — M192+. Международный масштаб и статус «лучше лучших»

Расширение через измеренное качество: реальные конкуренты, blind benchmark, внешняя оценка, удовлетворённость пользователей, удержание, экономическая эффективность, SLA, безопасность и доступность. «Лучше в мире» возможно утверждать только в конкретном сегменте, по заранее заданным метрикам и независимым данным. Нельзя назначить себе 100% собственной панелью.

## Текущий блокирующий путь

**Исходный M181 → шесть канонических upstream → реальные конфликты и контракты → staging → независимые испытания → пользовательская ценность → подписанное owner-GO.**

До появления оригинальных upstream корректный статус: `M185 LOCAL SIGNED REVIEW TOOLING / PRODUCT INTEGRATION BLOCKED / PRODUCTION NO-GO`.
