# OSGARD DIRECTOR — план выхода к конкурентоспособной мировой платформе

**Версия:** M183, 27 октября 2026. **Статус:** ENGINEERING READINESS TOOLING / SIX-PRODUCT RELEASE NO-GO.

## Что именно должно стать продуктом

**Кандидат на продуктовую гипотезу (не утверждённая пользователем спецификация):** OSGARD — единая платформа, в которой человек формулирует цель, ИИ-помощник предлагает проверяемый план, шесть специализированных подсистем выполняют разрешённые операции, пользователь получает воспроизводимый результат и прозрачный отчёт о стоимости, безопасности, происхождении материалов и эффективности.

**Принцип отличия:** управлять достижением пользовательского результата, а не шестью отдельными панелями; действие ИИ должно быть объяснимым, ограниченным правами, воспроизводимым и обратимым, если это технически возможно. Важные действия выполняются только с явным разрешением пользователя.

**Предлагаемый минимальный сквозной пользовательский сценарий:**

1. Пользователь выбирает цель и рабочую область.
2. NEXUS предлагает план, стоимость и границы разрешений; пользователь подтверждает важные действия.
3. ORBITAL приводит подтверждённые данные для выбора решения (при наличии надёжных источников).
4. TITAN/KRAKEN исполняет только разрешённые фоновые операции в изолированной среде.
5. GENESIS создаёт допустимые материалы, HUMAN EXPERIENCE показывает результат с доступным UX.
6. COMMERCE обрабатывает только реальные согласованные платежи, с идемпотентностью и аудитом.
7. Пользователь получает результат, журнал доказательств, отказ от небезопасных действий и возможность экспорта.

**Ни один пункт выше не подтверждён как готовый интегрированный пользовательский сценарий.** Это критерий для vertical slice, а не описание текущего production.

## Этапы — по крупным продуктовым блокам

### M184 / Origin — канонические исходники и ответственность

**Работа:** сверить оригинальные архивы M180 и M181 с независимыми SHA, восстановить подлинный TASK_BOARD 180/294, установить и задокументировать настоящие владельцев и SHA всех шести продуктовых upstream. Историческая C9-ветка допускается только как отдельный reference, пока byte-level связь с M181 не доказана. 28 конфликтов восстановить как настоящие пути и hashes, не placeholders.

**Условие выхода:** 6/6 source mappings, 180/180 оригинальных ID, 294/294 зависимости; архивы проверены, Git lineage и владельцы подтверждены. До этого изменения в продуктовых репозиториях запрещены.

### M185 / Trust — безопасность и контракты

**Работа:** общий IAM/RBAC/SSO, tenant isolation, sandbox, secrets, threat model, SBOM, лицензии шрифтов STYLO, запрет импортировать временную SQLite и кэши, девять оригинальных producer/consumer API контрактов; независимое разрешение 17 P0 + 11 P1 конфликтов.

**Условие выхода:** 28/28 оригинальных решений с различными author/reviewer и CI на точном SHA; 9/9 версионированных контрактов с positive/negative E2E в staging; требования безопасности выведены из применимого OWASP ASVS 5.0.0 и подтверждены аудитором. Никаких автоматических production approvals.

### M186 / First user outcome — единый рабочий сценарий

**Работа:** один завершённый вертикальный сценарий через все шесть подсистем, единая авторизация, единая история результатов, понятно оформленные действия ИИ и разрешения пользователя; платёжный путь сначала в sandbox, без живых транзакций. Адаптивный RU/EN интерфейс, доступность, ручное тестирование клавиатуры и мобильных устройств.

**Условие выхода:** реальный пользователь достигает заранее определённого результата end-to-end, включая отказ, возобновление, экспорт и объяснение ошибок; в логах указаны реальные SHA каждого сервиса. Сейчас такого доказательства нет.

### M187 / Reliability — работа под нагрузкой

**Работа:** tracing, metrics, logs (OpenTelemetry), продуктовые SLI/SLO, incident/on-call, нагрузочные тесты, восстановление из backup, ротация ключей, проверки сети и данных. Отдельные замеры p50/p95/p99, цена/задание, процент отказов, длительность восстановления.

**Условие выхода:** реальные воспроизводимые прогоны на staging среды с опубликованным budget; владелец продукта утверждает SLO только после baseline. Google SRE рекомендует error budgets для управления риском изменений — локальные тесты такого бюджета не заменяют.

### M188 / Product-market proof — первые независимые пользователи

**Работа:** выбрать узкий целевой сегмент и конкурентов по идентичным пользовательским задачам; интервью, оплачиваемые пилоты при согласии клиентов, анализ времени до ценности, воронки конверсий, повторного использования, причин отказа. Без хранения ненужных персональных данных.

**Предлагаемые критерии пилота для обсуждения (не фактические результаты):** не менее 20 интервью; 10 пилотных команд; 70%+ завершения конкретной полезной задачи без ручного вмешательства; измерение Retention D7/D30 на реально сформированных когортах; сравнение 3 альтернативных решений одним протоколом. Не утверждать проценты до появления измерений.

### M189 / Independent release — доказательство готовности

**Работа:** независимые security и UX ревью, production-like rollback, продуктовый E2E на точном SHA, финансовые и юридические ограничения, готовность поддержки, восстановление из инцидента, лицензии и политика данных, отдельное осознанное решение владельца о запуске.

**Условие выхода:** все 180 оригинальных ID приняты независимыми ревьюерами после закрытия зависимостей; 28 конфликтов и 9 контрактов подтверждены; все 32 мировых критерия получают адекватные для продукта доказательства или обоснованный неприменимый статус; release owner принимает решение на основании данных. Даже выполнение перечня не даёт объективного титула «лучший в мире» — он требует успехов на рынке и сопоставимого сравнения.

## Примерные рыночные и инженерные ориентиры — НЕ утверждённые SLA

| Область | Начальный обсуждаемый порог | Метод подтверждения |
|---|---|---|
| Сервис | SLO доступности >= 99.9% для критической операции | 30 дней фактических user-impact SLI |
| Скорость | p95 для типового интерактивного API — целевой бюджет после baseline | Load-test той же версии, профили запросов и сеть |
| Восстановление | RTO/RPO определяются ценностью данных и риском | Реальный restore drill с SHA/ledger |
| UX | WCAG 2.2 AA для релевантных пользовательских путей | Автоматический + независимый ручной аудит |
| AI | Domain-appropriate accuracy, risk/latency/cost budgets | Blind human eval, red-team, pinned test set |
| Рынок | Retention D7/D30, paid pilots, completion rate | Реальные обезличенные события и когорты |
| Поставка | DORA throughput/instability без ухудшения стабильности | Реальные GitHub deploys, incidents и recovery |

Цифры для p95, accuracy, RTO и paid conversion должны утверждаться с учётом конкретного продукта и покупателей: не придумывать их сейчас.

## Что запускается до получения M181

Шесть задач класса A01 — только безопасный поиск оригинальных исходников, owners и Git refs. Оригинальный M181 ZIP и source task crosswalk должны появиться до любой автоматизации B/C/D. Отдельные рабочие проекты `osgard-world` и `osgardos` не заменяют эти upstream.

**Приёмочный статус M183:** инструмент готов для независимого ревью; производственная интеграция не начата; `PRODUCTION_NO_GO`.
