# OSGARD SUPREME DIRECTOR — M205 / Контроль стоимости

Четыре крупных блока локального кода поверх M204 на существующей SQLite: сверка затрат M198↔M204, защита от двойного счёта, регулярные затраты и net-ROI по сценариям владельца, русская панель с CSV и CI.

## 1. Сверка источника расходов M198↔M204

Операции:
- commerce.reconcile.inspect — список связанных/непривязанных затрат и кандидатов из M198;
- commerce.reconcile.link — явное сопоставление M204 economic_entry_id с M198 project_id / expense_id;
- commerce.reconcile.unlink — разрыв связи с обязательной причиной и сохранённым событием;
- commerce.reconcile.portfolio / portfolio.csv — общая сводка организации.

Разрешается связывать только активные записи одного tenant, с равной суммой, видом затрат и актуальной версией. planned ↔ cost_planned, incurred ↔ cost_incurred. Каждая запись M204 и каждый расход M198 могут иметь не более одной активной связи. Через host/version checks обнаруживаются удалённые, отменённые и изменённые источники. Предложенные совпадения не подтверждаются автоматически.

**M198 является только локальным источником проверки.** В ROI учитывается один раз стоимость M204, а сумма M198 повторно не добавляется. Это НЕ сверка с банком: две вручную введённые записи могут ошибочно совпадать.

## 2. Регулярные расходы на срок 1–36 месяцев

Операции:
- commerce.recurring.add / void — добавление либо отмена с причиной, version CAS и идемпотентностью;
- commerce.recurring.list / calendar — помесячные затраты по выбранному плану и basis.

Запись содержит plan_id, basis (planned или reported), amount_minor (целые копейки RUB), start_month, end_month, evidence_note и reference. Активные записи в одной категории нельзя дублировать по reference.

История хранится в append-only events с SHA-256 chain. При каждом чтении система сверяет конечные строки и события; внешнего доверенного якоря нет. Заявленная владельцем регулярная стоимость не является подтверждённой оплатой.

**Пустой список регулярных затрат — неизвестность, а не ноль.** Для расчёта без записей необходимо явно указать assume_zero_recurring=true; это лишь заявленное пользователем допущение, не доказанный нулевой расход. Если записи есть, противоречащее им допущение отвергается.

## 3. Net-ROI и устойчивое возвращение вложений

Операция commerce.economics.net_scenarios требует:

    {
      "plan_id": "<existing M203 plan UUID>",
      "cost_basis": "incurred",
      "recurring_basis": "reported",
      "horizon_months": 12,
      "realization_rates_bp": [5000, 7500, 10000],
      "require_reconciled_costs": true,
      "assume_zero_recurring": false
    }

За каждый месяц:
- Gross = floor(M204 forecast_monthly × realization_rate_bp / 10000).
- Net = Gross − сумма регулярных затрат M205, действующих в этом месяце.
- Cumulative = − разовая стоимость M204 выбранного basis + сумма Net за месяцы 1..N.
- Projected ROI (bp) = floor(Cumulative at horizon × 10000 / разовая стоимость).
- Payback month = первый месяц, когда Cumulative >= 0.
- Sustained payback = первый месяц, начиная с которого Cumulative не уходит ниже нуля до конца выбранного горизонта.

10 000 basis points (bp) соответствуют 100% ROI. Если нет инвестиционной базы, гипотезы месячной выгоды, подтверждённой нулевой стоимости или обязательной сверки, прогнозный ROI/payback возвращает null с объяснением причины. При устаревшей связи M198 ROI блокируется даже в режиме ручной стоимости.

Если require_reconciled_costs=false, допускаются ручные затраты M204 с явной маркировкой. Доказательства причинной связи, банковской оплаты, реального возврата и незапланированных налогов этот расчёт не предоставляет. Регулярные и разовые выплаты разделены; self-reported разовая выгода не подмешивается в прогноз.

## 4. Портфель, русская панель и безопасность

Локальный адрес после запуска: **http://127.0.0.1:8725/cost-control/**.

В панели: выбор M203 plan, подтверждение совпадений, устаревшие источники, ведение месячных затрат, три изменяемых сценария, первый/устойчивый срок окупаемости, таблица по месяцам, отчёт по организации и CSV. Экспорт защищён от spreadsheet formula injection.

Доступ только owner соответствующей организации; нет HTTP listener вне loopback, CDN, email, push, мессенджеров, платежей, автоматического фонового запуска. Токен хранится только в памяти вкладки, а события защищены локальной проверяемой цепочкой без внешней подписи.

### Как запустить

Из корня GitHub-репозитория, Python 3.11+:

    export PYTHONPATH="$(pwd)/supreme-director/m192:$(pwd)/supreme-director/m193:$(pwd)/supreme-director/m194:$(pwd)/supreme-director/m195:$(pwd)/supreme-director/m196:$(pwd)/supreme-director/m197:$(pwd)/supreme-director/m198:$(pwd)/supreme-director/m199:$(pwd)/supreme-director/m200:$(pwd)/supreme-director/m201:$(pwd)/supreme-director/m202:$(pwd)/supreme-director/m203:$(pwd)/supreme-director/m204:$(pwd)/supreme-director/m205"
    python3 -m osgard_m205 init --db ./director-local.sqlite --tenant "Моя компания"
    python3 -m osgard_m205 serve --db ./director-local.sqlite --port 8725

Windows: разделяйте каталоги PYTHONPATH символом ; вместо : .

Для **уже существующей базы M204** не используйте init. Остановите предыдущий сервер, создайте проверенную резервную копию SQLite с учётом WAL, запустите только serve с прежней БД. Новая схема добавляет таблицы, индексы, триггеры; данные M192–M204 не перезаписывает.

M205 сохраняет one-shot CLI проверки расписания M202 с передачей токена через stdin:

    python3 -m osgard_m205 run-due --db ./existing.sqlite --token-stdin

Фоновый планировщик не устанавливается автоматически.

### Границы и выпуск

- Сверка локальных записей и SHA-256 не заменяют независимый финансовый аудит.
- Нет реального bank feed, реальных платежей, внешней сверки и доказанного экономического ROI. Не все возможные дубли ручных расходов можно обнаружить.
- Сценарии не моделируют налоги, финансирование, амортизацию, инфляцию и фактическое поступление денег.
- Физическая мобильная визуальная приёмка отдельно необходима.
- Исходные 180 upstream задач **0/180 независимо приняты**; production NO-GO, PR остаётся Draft, main не меняется.
