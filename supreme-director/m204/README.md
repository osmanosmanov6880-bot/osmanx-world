# OSGARD SUPREME DIRECTOR M204 — Экономика решений и приоритеты

**Четыре больших блока настоящего локального кода** поверх M203: журнал расходов и заявленной выгоды, сценарный ROI с проверкой полноты данных, субъективный портфель приоритетов, русская адаптивная панель с CSV и CI. Модуль использует действующие планы M203 на SQLite M192–M203.

## Блок 1 — Раздельные финансовые записи

Операции: commerce.economics.entry.add, entry.void, ledger.

Виды записей:
- cost_planned — плановые **разовые** затраты;
- cost_incurred — **заявленные владельцем** понесённые затраты (не проверены по банку);
- benefit_forecast_monthly — ожидаемая выгода в месяц, гипотеза;
- benefit_reported_once — **заявленная** разовая выгода, после ручной проверки результата M203.

Все суммы хранятся **целыми копейками, RUB**. Каждая запись содержит объяснение и при необходимости ссылку на источник. Для заявленной выгоды обязательно указать уникальный reference и evaluation_id последнего принятого M203 результата. Это лишь связывает заявление с модельным наблюдением, но не делает его доказанной прибылью.

Повторяющийся reference в одной категории блокируется; повторная запись с тем же идемпотентным ключом возвращает тот же результат. Удаление заменено на void с обязательной причиной, а история дополнена локальной SHA-256 цепочкой. При чтении цепочка пересчитывается и **сверяется с текущими строками**. Триггеры запрещают изменение и удаление событий. Внешнего независимого якоря нет.

## Блок 2 — Явные сценарии ROI и срока окупаемости

Операция commerce.economics.scenarios требует plan_id, cost_basis (planned/ incurred), horizon_months (1–36) и ТРИ самостоятельно заданных коэффициента realization_rates_bp (0–10000 bp) в возрастающем порядке.

Расчёты:
- monthly_forecast = сумма **только benefit_forecast_monthly**;
- investment = сумма **либо cost_planned, либо cost_incurred**, по явно выбранной базе. Эти базы НИКОГДА не складываются;
- assumed_monthly = floor(monthly_forecast × realization_rate_bp / 10000);
- benefit_in_horizon = assumed_monthly × horizon_months;
- projected_roi_bp = floor((benefit_in_horizon − investment) × 10000 / investment);
- projected_payback_months = ceil(investment / assumed_monthly), если assumed_monthly больше нуля.

10000 basis points (bp) = 100% ROI. Срок окупаемости условен: предполагает постоянную выгоду и **разовую** стоимость внедрения, без скрытых расходов. Не учтены сезонность, стоимость капитала и регулярная поддержка, если они отдельно не заложены во входные данные. Это **не прогноз по реальным платежам**.

Если инвестиция в выбранной категории или ежемесячная гипотеза отсутствует, ROI и payback возвращают null с кодом причины, **не ноль**. Нулевой коэффициент реализации, заданный пользователем, означает явный пессимистичный сценарий, а не неизвестность.

Отдельно рассчитывается claimed_roi_bp только при наличии **самостоятельно заявленных** cost_incurred и benefit_reported_once; вывод всегда помечен UNVERIFIED_SELF_REPORTED_RETURN. Никакого объединения прогнозной и заявленной выгоды в один ROI.

## Блок 3 — Очередь задач по явным оценкам владельца

Операции commerce.economics.priority.set/board. Для каждого плана владелец вручную оценивает срочность, важность, трудоёмкость и уверенность от 1 до 5 с обязательным пояснением. Прозрачная формула: score = urgency × impact × confidence / effort; хранение score_x100 в целых числах (баллы ×100).

Версии, идемпотентность и экономическая история изменения оценки контролируются на сервере. Планы без оценки **не получают искусственный ранг** и выводятся отдельно после оценённых. Порядок субъективен, **не является математическим прогнозом выгоды**. Неведомый ROI нельзя считать нулевым для ранжирования.

## Блок 4 — Русский OBSIDIAN UI, отчёт и проверка

Локальный адрес: http://127.0.0.1:8724/economics/

В панели: выбор плана M203, ввод затрат и выгоды, проверяемый журнал/void, три редактируемых сценария, ручная приоритизация, портфель. Отдельные commerce.economics.portfolio / portfolio.csv дают JSON и CSV UTF-8 c BOM, formula-injection guard.

**Доступ только tenant owner.** Сотрудники видят свои задачи M195/M203 в соответствующей области, а не бюджет и ROI M204. HTTP сервер только loopback, host/origin guards, CSP, токен в памяти вкладки, никакого localStorage. Продукт не отправляет почту, мессенджеры и не выполняет платежи.

### Первый запуск

Из корня GitHub-репозитория (Python 3.11+):

    export PYTHONPATH="$(pwd)/supreme-director/m192:$(pwd)/supreme-director/m193:$(pwd)/supreme-director/m194:$(pwd)/supreme-director/m195:$(pwd)/supreme-director/m196:$(pwd)/supreme-director/m197:$(pwd)/supreme-director/m198:$(pwd)/supreme-director/m199:$(pwd)/supreme-director/m200:$(pwd)/supreme-director/m201:$(pwd)/supreme-director/m202:$(pwd)/supreme-director/m203:$(pwd)/supreme-director/m204"
    python3 -m osgard_m204 init --db ./director-local.sqlite --tenant "Моя компания"
    python3 -m osgard_m204 serve --db ./director-local.sqlite --port 8724

На Windows между каталогами PYTHONPATH должен быть символ ; вместо : .

### Обновление существующей базы M203

1. Остановите предыдущий сервер.
2. Сохраните и протестируйте SQLite backup **с учётом WAL**.
3. Запускайте M204 только через serve --db ./existing.sqlite, **не init**. Новая схема добавляет таблицы и индексы; существующие данные M192–M203 не удаляются.
4. Проверьте прежние операции CRM и новые экономические разделы.

CLI M204 сохраняет one-shot run-due от M202 с передачей владельческого токена через stdin. Настройка системного расписания вручную.

### Автотесты

    python3 -m unittest discover -s supreme-director/m204/tests -p 'test_*.py' -v
    python3 supreme-director/m204/smoke.py
    node --check supreme-director/m204/osgard_m204/web/app.js

CI выполняет регрессии **всех M192–M203** на Python 3.11/3.13 и сквозную проверку. Успех тестов не означает, что была проведена физическая визуальная приёмка на телефоне.

## Ограничения и production gate

- Нет интеграций с банком, платёжных поручений, верифицированных денежных эффектов или независимой финансовой проверки.
- ROI рассчитан **по явным ручным допущениям**. Показатель из модели M203 не доказывает причинную связь между работой сотрудника и выручкой.
- Некоторые расходы на проекты M198 могут дублировать ручной журнал M204, если владелец внесёт их дважды с разными ссылками. Система блокирует одинаковые ссылки внутри категории, но без банковских данных не может обнаружить все внешние дубли.
- Первоначальные 180 upstream-заданий **0/180 независимо приняты**. Это локальная инженерная ветка, не production. Merge в main и публичный деплой запрещены до отдельной приёмки.
