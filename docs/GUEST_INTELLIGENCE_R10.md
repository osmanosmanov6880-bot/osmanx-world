# OSMANX Guest Intelligence R10 — production readiness without unsafe deployment

18 ноября 2026. Предыдущий релиз R9: commit f935a28b2cabe9a7409adb166788c92b4ef612a6.

**Разница между четырьмя состояниями:**
1. Публичный статический интерфейс R9 опубликован на osmanx.world.
2. Серверный код и миграции могут быть проверены в изолированном CI.
3. Staging API может быть запущен уполномоченным оператором локально.
4. Production API и разрешение собирать клиентские данные — отдельное решение после проверки прав, защиты, бэкапа и юридических условий.

Первые три состояния сами по себе НЕ означают четвертое. Действующая учётная запись deploy-osmanx не обладает полномочиями для Docker, установки PostgreSQL и правки Nginx. R10 их не обходит.

## Пять реализованных инженерных блоков

### 1. Версионная публичная проверка R9 — исправлена устаревшая проверка R5

Ранее скрипт guest-readiness.mjs искал старый заголовок «Закрытый кабинет», поэтому опубликованный интерфейс R9 мог ошибочно считаться отсутствующим. R10 проверяет реальный заголовок R9, страницу приглашения, две health-точки, ожидаемую миграцию 008_guest_actions_and_imports.sql, leastPrivilege, forcedRls, гостевые записи и анонимный отказ 401 у маршрутов пилотов, доказательств, диагностики, действий и импорта.

Разрешены только HTTPS osmanx.world или специальный loopback в тестовом режиме; запросы только GET, без cookie, Authorization, токенов и редиректов. Результат различает staticReady и apiReady. Защищённый API не считается запущенным по факту наличия HTML.

Команда только для чтения:
    node scripts/guest-readiness.mjs --report

Строгий внешний контроль (ожидаемо может завершиться NO-GO, пока API не развёрнут):
    node scripts/guest-readiness.mjs --require-api

### 2. Server-side fail-closed guard

При NODE_ENV=production приложение не начинает прослушивание порта, пока не подтвердит схему PostgreSQL, все семь Guest-таблиц с FORCE RLS и отсутствие лишних привилегий runtime-роли. При GUEST_WRITES_ENABLED=false любые Guest POST/PATCH/PUT/DELETE отклоняются 503.

Даже если оператор вручную включает GUEST_WRITES_ENABLED=true, сервер перед каждой Guest-мутацией повторно проверяет актуальность миграций и защиту RLS. При отказе БД, пропущенной миграции, BYPASSRLS или нарушении ограничений записи отклоняются 503. Cookie, Origin, CSRF и роли продолжат проверяться отдельно. Никакой операторский флаг не отменяет эти уровни безопасности.

В test/guest-r10-guard.test.mjs есть как успешные, так и негативные сценарии. Ошибки не включают пароль, SQL-DSN и строку подключения.

### 3. Полноценная двухсотрудниковая приёмка по реальному HTTP

test/guest-r10-real-http.test.mjs запускает Fastify на случайном локальном порту в production-конфигурации с Secure/HttpOnly/SameSite cookie, но подключает только синтетическую PostgreSQL industry_ci на 127.0.0.1. Прежде чем начать, тест сверяет оба DB URL и NODE_ENV=test.

Цепочка:
- Владелец собственной компании и отдельный владелец чужой компании.
- Гостевые записи выключены по умолчанию, ответ 503.
- Одноразовое приглашение управляющего, отдельный пароль/сессия, replay приглашения запрещён.
- Включение записи только в изолированном тестовом процессе; сессия, CSRF и чужой Origin по-прежнему обязательны.
- Заявка → квалификация другим сотрудником → протокол → готовность → запуск.
- Диагностика без данных, запись управленческого действия, отдельный исполнитель.
- CSV предпросмотр, отказ при неверном SHA-256, атомарный импорт двух агрегированных периодов, идемпотентный replay.
- Запрет владельцу подтверждать собственную подачу; независимая приёмка другим сотрудником.
- Пересчёт evidence.v2 SHA-256, архивирование владельцем, отзыв управляющего и проверка сохранённой истории.
- Чужая компания не может читать пилот, доказательства и чужие заявки.

Это реальный сетевой HTTP к изолированной тестовой БД, не утверждение о существующих клиентах или боевом API.

### 4. Доказательства v1 и v2 после восстановления двумя независимыми age-ключами

scripts/dr-guest-proof.mjs дополнительно сохраняет синтетический протоколированный архив evidence.v2 с двумя агрегированными периодами, внутренним submitted_digest, независимым решением управляющего и аудитом. В CI после создания зашифрованного архива оба независимых age identity восстанавливают данные каждый в собственную пустую БД. Проверка пересчитывает исторический SHA-256 v1, новый SHA-256 v2, журнал действий и импортов R9, роли проверяющих, историю audit/outbox и защиту RLS.

Целевые хосты и базы при этом жёстко ограничены тестовым loopback. Продуктивная база не затрагивается. Это восстановление тестовой копии, не фактическое подтверждение наличия офсайт-бэкапа VPS.

### 5. Независимый операторский GO/NO-GO для изолированного staging

scripts/r10-stage-gate.mjs читает только семь JSON-маршрутов HTTP на 127.0.0.1:3149. Требуется migration 008, forcedRls=true, leastPrivilege=true, guestWritesEnabled=false и 401 для всей приватной Guest поверхности. Не делает POST и не сохраняет пароли.

ops/r10-operator-gate.sh проверяет приватный файл настроек вне репозитория, отсутствие симлинков, локальный default Docker context, работу daemon, валидность отдельного Compose staging, целостность исходного tar.gz + SHA256SUMS и успешность сетевой проверки staging. Ничего не развёртывает, не обновляет Nginx, не создаёт пользователей, не запускает миграции и не даёт разрешения на настоящих клиентов.

Новый manifest osmanx.industry.r10.release.v1 фиксирует текущую миграцию, значение guestWritesDefault=false и ревизию исходников. CI проверяет повторяемость исходного архива, отказ повреждённому архиву, синтаксис операторских скриптов и реальный локальный staging. Проверка должна отклонять заданный DOCKER_HOST/удалённый Docker context.

## Операторские действия (НЕ выполнены на production VPS)

Только при наличии отдельного административного доступа, закрытой конфигурации и проверенного резервного восстановления:

    cd services/industry-api
    bash ops/build-release.sh /private/release-output
    bash ops/verify-release.sh /private/release-output/osmanx-industry-<commit12>.tar.gz
    bash ops/stage-launch.sh plan /private/staging.env
    R7_STAGE_ACK=CONFIRM_ISOLATED_STAGE_ONLY bash ops/stage-launch.sh apply /private/staging.env
    bash ops/r10-operator-gate.sh /private/staging.env /private/release-output/osmanx-industry-<commit12>.tar.gz

После проверки отдельным тестовым сотрудником:

    R7_STAGE_ACK=CONFIRM_ISOLATED_STAGE_ONLY bash ops/stage-launch.sh stop /private/staging.env

Заменить <commit12> фактической короткой ревизией архива. Не размещать .env или age private keys на общедоступном сайте, в GitHub и в логах. Запрещено удалять том PostgreSQL через docker compose down -v.

## Чего ещё нет

- Включения production API, реального PostgreSQL на доступном VPS и Nginx-прокси.
- Двух реально авторизованных сотрудников клиента и подписанного клиентом договора.
- Подтверждённого внеплощадочного резервного восстановления именно production-данных.
- Официально подтверждённой обработки персональных данных, оснований для маркетинговых контактов и SLA.
- Рабочих Stripe/VAT/рублёвых платежей, подписок или доказанной причинной прибыли.

До этих этапов выпуск клиентского кабинета разрешён только как статический интерфейс и синтетический staging. Никаких обходов прав на VPS.
