# OSMANX Guest Intelligence R8 — строгие пилоты и управление данными

Дата: 18 ноября 2026. Изменения относятся к сервису Industry API и статическому кабинету Guest Intelligence.

## Пять полноценных блоков

**1. Замороженный протокол исследования.** Создание нового пилота через POST /api/industry/v1/guest/pilots теперь обязательно включает protocol с полями:
- startDate/endDate (YYYY-MM-DD, период 1–90 дней);
- outcomeWindowDays (1–90 дней, единый критерий повторного визита);
- allocation (random / matched);
- source (pos / crm / manual);
- primaryMetric = repeat_visit.

В таблице guest_pilots протокол и timestamp регистрации сохраняются одновременно. PostgreSQL-триггер запрещает последующие изменения через UPDATE. Это защищает от изменения метрики после просмотра результатов. Если протокол зафиксирован **после начала** периода, система прямо сообщает о ретроспективном риске; она не утверждает, что исследование зарегистрировано заранее. Исторические записи без протокола остаются читаемыми, но не могут получить новый старт/отправку через защищённый API.

**2. Честное окно наблюдения и доказательства v2.** Дата агрегированного периода обязана находиться в зафиксированных границах исследования и не может быть будущей. Отправка на независимый разбор запрещена до окончания endDate + outcomeWindowDays. В SHA-256 слепка v2 включаются план, готовность, target, сам протокол, timestamp его регистрации и упорядоченные обезличенные показатели. Результаты и статус остаются только сценарной аналитикой без гарантии прибыли и без утверждения причинного эффекта. Исторический слепок v1 не пересчитывается и продолжает восстанавливаться после DR.

**3. Лимиты и защита компаний при конкурирующих запросах.** Миграция 007 добавляет tenant-scoped guest_quotas с FORCE RLS, SELECT-only для runtime industry_app. По умолчанию 250 обращений за последние 365 дней и 50 неархивированных пилотов. DBA может устанавливать более строгие значения, но ни HTTP-клиент, ни пользователь приложения не могут их менять. Перед созданием заявки/пилота используется транзакционная блокировка по tenant. Повторная заявка с тем же Idempotency-Key возвращает исходную запись даже при полной квоте. Изолированные одновременные записи должны привести к одной успешной операции и одному HTTP 429 при квоте 1.

**4. Показатели владельца и ограниченное хранение.** GET /guest/overview доступен owner/manager: численности заявок по состояниям, пилотов по стадиям, квоты и агрегированное число наблюдений. Нет контактных данных людей или отдельных гостей. Названия заявок и пилотов отвергают явно распознаваемые email/телефоны (это дополнительная, **не абсолютная** защита от персональных данных). Владелец может выполнить POST /guest/requests/retention с {"confirm":true}. До 100 отклонённых и не связанных с пилотом заявок, чьё обновление было более 90 дней назад, теряют свободный текст названия. Их IDs, статусы, следы аудита и связи остаются. Запуск только по явному подтверждению; автоматического удаления документов, архивов и финансовых результатов нет.

**5. Реальный UI и регрессионная приёмка.** Русский кабинет предлагает даты/метод/источник до создания, отображает неизменяемый протокол и риск регистрации задним числом, показывает только актуальный серверный overview и использует защищённый маршрут очистки. На PostgreSQL 16 тестируются несколько независимых компаний, защита RLS, 400/409/429, неизменяемость даже при прямом SQL UPDATE, проверка SHA-256 и старые сценарии R4–R7. Chromium проверяет логин, приглашения, заявки/пилоты, новые поля и мобильный UI. DR CI обязан восстановить исторический v1 без потери digest; release CI обновляет последний требуемый SQL до 007.

## Пример тела POST /guest/pilots

    {
      "title": "Повторные визиты, пилот A",
      "plan": {
        "baselinePct": 20, "liftPp": 10,
        "margin": 250, "discount": 10, "fixed": 0, "fee": 25000
      },
      "protocol": {
        "startDate": "2026-12-01", "endDate": "2026-12-14",
        "outcomeWindowDays": 14,
        "allocation": "random",
        "source": "pos",
        "primaryMetric": "repeat_visit"
      },
      "requestId": null
    }

Все маршруты, кроме анонимного /health, используют существующие сессионные cookie, Origin, CSRF, права сотрудников и PostgreSQL tenant RLS. Для реального использования действуют также юридическая проверка источников агрегатов, условия договоров, сопоставимость групп и согласия на коммуникацию. Чекбоксы этого не заменяют.

## Безопасный релиз и откат

- Применение migration 007 обязательно до включения нового API. /health/ready должен вернуть version 007, forcedRls=true, leastPrivilege=true. Если нет — 503; запирать гостевые записи до готовности.
- Синтетические проверки должны пройти **до** развёртывания на настоящий VPS. Текущий deploy-osmanx не имеет Docker, Node, sudo и прав на Nginx; статическая публикация HTML не является запуском защищённого сервера.
- CI для PR: industry-api PostgreSQL, industry DR/age restore, Guest UI Chromium, воспроизводимый release-пакет. Слияние только если все обязательные проверки зелёные.
- Production API остаётся выключен через GUEST_WRITES_ENABLED=false. Переключать только после согласованного запуска отдельным авторизованным оператором, проверенного бэкапа/восстановления и двухсотрудникового staging-пилота.
- Миграция аддитивная: старые протоколы NULL и архивные SHA v1 сохраняются. Для отката приложения предыдущий образ может читать старые таблицы; **не удалять** новую схему и историю аудита. Статические страницы откатываются отдельным revert PR.
- Stripe, реальные счета, VAT и автоматические подписки здесь не включены.

**Интерпретация:** даже статистически заметное различие возвратов без добросовестного дизайна, контроля пересечений гостей и проверенных исходных данных не даёт права утверждать доказанный причинный рост прибыли.
