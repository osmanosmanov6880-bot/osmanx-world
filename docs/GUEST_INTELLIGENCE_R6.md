# OSMANX Guest Intelligence R6 — серверный релиз и изолированная приёмка

18 ноября 2026. PR #38, osmanosmanov6880-bot/osmanx-world.

## Инфраструктурное ограничение

Read-only аудит существующего VPS подтвердил: deploy-osmanx не имеет Docker, npm, Node.js, sudo, доступа к /opt и права изменять Nginx. Статический сайт публикуется, а работающий backend пока не установлен. Зелёный CI этого факта не отменяет. Никакой production сервис в этой версии автоматически не запускается.

## Пять реализованных блоков

### 1. Проверенный релиз

- services/industry-api/ops/build-release.sh создаёт воспроизводимый tar.gz из разрешённых файлов API: Dockerfile, compose.yml, package.json, src, shared, migrations, scripts и конкретных ops файлов.
- Без .env, приватных ключей, архивов базы и персональных сведений.
- На каждый файл генерируется SHA256SUMS, на весь архив — отдельный companion SHA256. Время, порядок файлов и gzip заголовок фиксированы.
- ops/verify-release.sh отклоняет подменённый архив, выход за границы каталога, ссылки и неожиданное число файлов.
- Контрольная сумма не является независимой подписью издателя. Источник скачивания обязан быть доверенным.

### 2. Настоящий HTTP с PostgreSQL

Тест test/guest-r6-http.test.mjs открывает реальный loopback HTTP-сокет Fastify на временном порту и использует отдельную PostgreSQL CI. Проверяются вход владельца, одноразовое приглашение и вход второго сотрудника, RLS, Origin/CSRF, заявка, пилот, независимое подтверждение, SHA-256, архив и отзыв прав. Этот тест не должен исполняться с production учётными записями.

### 3. Production write gate и секреты

В NODE_ENV=production любые операции изменения /api/industry/v1/guest/ возвращают 503, пока GUEST_WRITES_ENABLED явно не равно true. После включения всё ещё обязательны сессии, CSRF, роли и RLS.

node scripts/preflight.mjs /path/to/.env читает приватный файл без shell-eval и не печатает его значения. Контролирует права доступа, независимость 64-символьных DB секретов, email владельца, разрешённую организацию и независимые age-ключи. При попытке включить запись требуется специальный аргумент --allow-writes. Сам флаг не заменяет внешнюю юридическую и инфраструктурную приёмку.

### 4. GitHub artifact для отдельного оператора

.github/workflows/guest-r6-release.yml проверяет синтаксис, собирает один релиз дважды, сравнивает байты, проверяет восстановленный manifest, отвергает испорченную копию, импортирует Guest API в настоящем nonroot Docker и сохраняет tar.gz + sha256 в GitHub Actions artifact на 7 дней.

Этот workflow не копирует файлы на VPS, не читает живые серверные секреты, не создаёт пользователей и не запускает Nginx.

### 5. Стейджинг production Docker

ops/staging-smoke.sh запускается только в изолированном CI на локальном Docker context и синтетической БД industry_ci. Поднимает настоящий production image с запретом записи Guest, проверяет 200 на health, 401 на закрытых маршрутах, 503 на запросе записи и автоматически удаляет тестовый контейнер. Действующий сервер и клиентские базы не затрагиваются. Дополнительный модуль disaster recovery проверяет восстановление отдельными age-ключами.

## Контрольный путь администратора к production

1. Выделить отдельную управляемую серверную среду либо уполномоченного администратора VPS. Не повышать автоматически права deploy-osmanx и не менять существующий Nginx без review.
2. Скачать архив из зелёного GitHub Actions. Сверить ревизию, SHA256 и содержимое инструментом verify-release.sh. Распаковать вне /var/www; не публиковать архив на сайте.
3. Создать на сервере .env с правами 0600 и независимо хранимые age ключи. Установить GUEST_WRITES_ENABLED=false. Пройти preflight до попыток включения реальных клиентов.
4. Проверить резервное копирование и восстановление в изолированную PostgreSQL. После сверки цели применить отдельные DB роли и миграции; запустить API с портом только на loopback, без интеграционного worker. Не выполнять docker compose down -v.
5. Администратору проверить nginx -t, HTTPS, Cookie Secure/HttpOnly/SameSite, отсутствие публичного DB порта и отдельную резервную копию. Перед любыми действиями убедиться, что операционные команды обращаются к правильному серверу.
6. Проверить два независимых аккаунта и полный пилот в staging. Пока запись 503, показать эту блокировку как обязательную, а не обходить её. Получить официальное подтверждение законности данных, согласий и коммерческих условий.
7. Только после приёмки оператор может явно поменять GUEST_WRITES_ENABLED на true, выполнить preflight с --allow-writes и по регламенту перезапустить API. При сбое вернуть false и прежний образ, не удаляя PostgreSQL таблицы и журналы.

## Границы достигнутого

Все задания R6 — подготовка и тестирование системы на изолированной инфраструктуре. Без отдельного административного доступа production API на имеющемся VPS не запускается. Реальные оплаты, Stripe, VAT, автоматические подписки и юридически принятые клиентские пилоты не заявляются. SHA-256 не доказывает причинную связь или получение прибыли.
