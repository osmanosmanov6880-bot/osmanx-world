# OSMANX Guest Intelligence R20 — интеграционная приёмка и контроль первого клиента

Дата: 19 ноября 2026 года. Состояние: отдельная ветка/черновой PR поверх R19 #53. **Без слияния в main, без деплоя, без подключения реальных клиентов.**

## Пять полноценных инженерных блоков

1. **Верификация истории релизов R14–R19.** `scripts/r20-release-chain.mjs` в режиме `--github` использует исключительно GET к GitHub API. Для PR #47, #48, #49, #51, #52, #53 закреплены 40-символьные SHA, ожидаемые названия веток/основы и точные имена обязательных успешных CI jobs. Сравнение каждого соседнего коммита через immutable `/compare/sha...sha` не даёт подменить историю PR. Модель различает код, прошедший CI в черновиках, от реально слитой последовательности и отдельного списка ручных проверок. **Никогда не выводит автоматический `customerGo:true` или `productionActivated:true`.**
2. **Независимое решение о публикации с двумя Ed25519 подписями.** `scripts/r20-change-ticket.mjs` подписывает один ограниченный документ конкретного tenant/pilot, полный Git commit, SHA действующего R19 scope, внешний R18 anchor, отдельные SHA двухартефактного DR и off-site/WORM подтверждений, rollback snapshot и окно изменения сроком 1–120 минут, плюс срок билета до 24 часов. Два разных человека, роли `release_operator` и `independent_reviewer`; один и тот же ключ не подходит. Проверяется отсутствие повторного использования ключей хранителя R18 или подписанта R19. Никаких приватных ключей в репозитории, API или браузере. **Две криптографические подписи являются документальным свидетельством, но не правовым разрешением и не командой публикации.**
3. **Восстановление R18+R19 с подсчётом аудита.** `scripts/r20-restore-crosscheck.mjs` запускается только против заранее изолированной БД `industry_dr_*` на доверенной локальной DR-машине. Сначала отдельно проверяются подписанный R18 portable proof и контрольные точки R17/R18 через скрипт R18. Затем в новой `BEGIN READ ONLY` транзакции сверяются миграция 014, нужный пилот, отпечаток протокола, точный tenant, каждодневные `used_count`, `max_daily` и число append-only событий, а также возможное нарушение срока хранения из подписанной политики R19. Нет pg_restore, перезаписи, DDL/DML, поднятия STOP или включения производства. Любое несоответствие → `technicalRestoreReady:false`.
4. **Внутренняя панель контроля первого клиента.** Авторизованный `GET /api/industry/v1/guest/pilots/:id/r20/inspection` доступен только владельцу или управляющему нужной компании. Показывает R12 enrolment (без ложного утверждения о юридическом согласии), R13 hold, R16 permit, R17 witness, R18 anchor, R19 scope, период и оставшуюся дневную квоту, совпадение аудита и соблюдение границы хранения. В ответе только агрегаты и безопасные коды проблем. Русский кабинет показывает отдельно технические блокировки и **обязательные внешние проверки** релиза, восстановленного архива и законности. Браузер не может подписать, снять остановку, включить VPS или принимать решения о production.
5. **Сквозная приёмка и воспроизводимый релиз.** Negative-тесты всех перечисленных механизмов: подмена одного CI job, SHA/ветки/родителя, повторный ключ подписанта, устаревшая подпись, рассинхронизация `used_count` с событиями, старые данные, неверная БД, другой tenant, R19 STOP и read-only API. Повторно прогоняются старые R7–R19 HTTP/PostgreSQL и двухключевое AGE восстановление. Манифест пакета отмечает `releaseReviewSupportedR20:true`, полную Git SHA, обязательные исходники и `guestWritesDefault:false`; две сборки сравниваются побайтово.

## Операционная процедура (только read-only, без активации)

Из `services/industry-api` после предоставления read-only GitHub токена при необходимости:

    node scripts/r20-release-chain.mjs --github

Этот отчёт показывает фактическое положение черновых PR. Успешная сборка в ветке **не равна** успешному слиянию. Любой изменившийся SHA или неуспешная проверка прекращает готовность цепочки. Отдельная независимая проверка существующего R19 scope:

    node scripts/r19-first-client-rehearsal.mjs --tenant TENANT_UUID --pilot PILOT_UUID

Для сверки восстановленного архива (строго на отдельной офлайн/loopback DR-машине с уже восстановленной базой):

    DR_RESTORE_DB_URL=postgresql://...@127.0.0.1:5432/industry_dr_r20_audit \
      node scripts/r20-restore-crosscheck.mjs /private/r18-proof.json TENANT_UUID PILOT_UUID

Программа загрузит актуально действующий подписанный R19 scope, сверит его с архивом и реальной восстановленной базой, покажет коды ошибок и **не** инициирует восстановление. При изменении контрольной точки после создания архива старый scope может не подойти: не снижайте trust floor; создайте новый проверенный пакет независимыми операторами.

## Форма change ticket

JSON план создаётся независимым оператором, а не пользовательским браузером. Требуемые поля: `schema=osmanx.guest.r20.two-person-change-ticket.v1`, `ticketId`, `tenantId`, `pilotId`, `releaseCommit`, `r19ScopeDigest`, `r18AnchorDigest`, `drProofDigest`, `offsiteReceiptDigest`, `rollbackSnapshotDigest`, `createdAt`, `windowStart`, `windowEnd`, `expiresAt`.

План подтверждают два разных человека на независимых станциях, используя разные ключи Ed25519:

    GUEST_R20_SIGNING_ACTOR_ID=release-person \
      node scripts/r20-change-ticket.mjs sign release_operator /private/plan.json /private/release.key.pem /private/release.approval.json

    GUEST_R20_SIGNING_ACTOR_ID=independent-person \
      node scripts/r20-change-ticket.mjs sign independent_reviewer /private/plan.json /private/reviewer.key.pem /private/reviewer.approval.json

Два approval JSON помещают в массив `approvals` оригинального плана в порядке `release_operator`, затем `independent_reviewer`. Программная функция `verifyChangeTicket` принимает два доверенных публичных ключа, отдельно закреплённые R19/R18 ключи, действующий R19 scope и внешний evidence и сверяет все подписи. Этот артефакт ничего не публикует и никому не выдаёт платные/клиентские привилегии.

## Требования перед коммерческим запуском

Все PR R14–R20 должны пройти review, контролируемое слияние и актуальные CI на коммитах целевого релиза. Далее требуются письменный клиентский договор, проверенное законное основание обработки данных, сроки и механизм удаления, отдельный аудитор восстановления, два независимых оператора, действующая off-site/WORM квитанция, подтверждённый rollback и разрешённое окно изменения. В реальной инфраструктуре должен действовать мониторинг STOP и тест аварийного отключения. Ни один из этих шагов не выполняется автоматически.

**Границы:** данные для тестов синтетические. SQL FORCE RLS и append-only не защищают от суперпользователя БД. Квитанция WORM или юридический документ с SHA сами по себе не доказывают независимую аутентичность, наличие согласия либо отсутствие ошибок обработки. `customerGo`, `legalGo` и `productionAuthorized` всегда false в автоматических ответах.
