# OSMANX Guest Intelligence R12 — независимый допуск первого пилота

18 ноября 2026. Основа: R11. Миграция: 010_guest_launch_gate.sql. Статика: R12. Production API ещё не запущен.

## Пять полноценных инженерных блоков

### 1. Неизменяемая PostgreSQL-таблица

Миграция 010 создаёт поле guest_pilots.launch_gate_enrolled_at и таблицу industry.guest_launch_attestations. Старые пилоты остаются без обязательного R12-допуска; владелец отдельно включает режим для выбранного draft. Включение однонаправленное, после чего нельзя сбросить поле даже прямым SQL UPDATE.

Таблица содержит tenant_id, pilot_id, actor_id, роль owner/manager, SHA-256 текущего протокола и условий, версию пилота, idempotency key, accepted_at и expires_at (до 14 суток). Включены ENABLE/FORCE RLS, runtime получает только SELECT/INSERT, триггер отвергает UPDATE/DELETE, миграция не удаляет исторические R8–R11 записи.

### 2. Проверяемые правила запуска

guest-launch.mjs выполняет 11 независимых проверок: включён ли режим; пилот в черновике; протокол существует; протокол зарегистрирован до начала измерения; период ещё действует; все шесть условий готовности истинны; в организации есть действующий владелец; есть действующий управляющий; актуальная отметка владельца; актуальная отметка управляющего; это разные сотрудники.

SHA-256 связывает pilot ID, версию, immutable protocol, дату его регистрации, расчётную выборку и все шесть readiness-флагов. Даже если изменить условия и потом вернуть старые значения, прежние подтверждения не восстановятся, потому что версия пилота выросла. Смена роли, удаление доступа или деактивация сотрудника сразу лишают его отметку силы. Весь вывод детерминированный и не требует AI.

### 3. Защищённый API и невозможность обойти UI

- GET /guest/pilots/:id/launch/gate — полный список причин, блокирующих запуск.
- POST /guest/pilots/:id/launch/enroll — только owner и confirm=true, запись необратима и меняет версию пилота.
- POST /guest/pilots/:id/launch/attest — владелец или управляющий подтверждает текущую версию, строго через CSRF, Origin, Idempotency-Key и tenant RLS.
- GET /guest/pilots/:id/launch/evidence.json — owner/manager видит журнал и SHA-256.

В существующем POST /guest/pilots/:id/start добавлен SERVER-SIDE контроль: если R12 включён, запуск отклоняется с 409 до двух независимых действующих подтверждений. Режим старых пилотов и ранее опубликованные доказательства v1/v2 не изменяются.

### 4. Проверяемый пакет допуска

Экспорт osmanx.guest.launch.export.v1 включает SHA-256 исходных агрегатов, актуальную проверку всех условий и максимум 100 событий подтверждения с ролями, аккаунтами и датами действия. Пакет содержит дополнительный SHA-256 всего JSON snapshot. Браузер проверяет SHA через Web Crypto до скачивания файла.

Контрольная сумма подтверждает только целостность файла; это не электронная подпись, не доказательство законности получения данных гостей, не договор, не доказательство роста выручки или оплаты.

### 5. Русский интерфейс и сквозная приёмка

В кабинете R12: список 11 условий, активация с явным подтверждением владельца, отдельная кнопка подтверждения собственной ролью, дата окончания каждого подтверждения, заблокированная кнопка старта при отсутствующих условиях, журнал запуска с контрольной суммой.

Приёмка: unit-тесты правил, PostgreSQL 16 (две независимые компании, roles, 409, replay, изменение условий, revoke, RLS, SQL-immutability), Chromium desktop/mobile, запуск и восстановление через два независимых ключа age, сохранение исторических evidence v1/v2 и нового R12-протокола, проверка воспроизводимого release manifest и HTTPS-маркера.

## Режим внедрения

R12 не запускает реальный production API, не устанавливает PostgreSQL на VPS, не меняет Nginx, не включает Stripe/VAT/подписки и не собирает реальные сведения гостей. Пользователь deploy-osmanx не имеет подтверждённых административных прав; их нельзя обходить.

Для реального пилота нужны отдельно: администратор VPS, offsite зашифрованное резервное копирование с восстановлением, согласованный протокол, законное основание обработки, действующие сотрудники, проверенные платежные/правовые документы и явный допуск оператора. GUEST_WRITES_ENABLED=false остаётся безопасным значением production по умолчанию. Не удалять БД/архивы при откате и никогда не запускать docker compose down -v.

**Операционный смысл:** два человека фиксируют ответственность до измерения, а система не позволяет запустить выбранный R12-пилот, пока контроль не завершён. Но это не разрешение на запуск сервера и не гарантия коммерческого результата.
