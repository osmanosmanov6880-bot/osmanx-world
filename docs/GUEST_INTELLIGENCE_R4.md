# OSMANX Guest Intelligence R4 — реальный серверный учёт пилотов

Дата: 18 ноября 2026. Код: services/industry-api/src/guest.mjs, миграция 004_guest_intelligence.sql, браузерный клиент assets/guest/console.html.

## Пять полноценных блоков

1. **Общие компании и защищённые аккаунты.** Переиспользуются Fastify 5, PostgreSQL 16, scrypt-пароли, HttpOnly cookie сессии, CSRF, Origin-check, роли owner/manager/operator/viewer. Четыре новые таблицы имеют FORCE ROW LEVEL SECURITY и составные tenant foreign keys. Публичная регистрация отсутствует, bootstrap и приглашения используют существующий API.
2. **Коммерческие заявки.** Авторизованный сотрудник создаёт заявку с названием задачи, каналом и состоянием new. Менеджер квалифицирует или отклоняет. Для создания нужен Idempotency-Key; повтор с теми же полями возвращает существующую заявку, с другим содержимым — 409. Квалифицированная заявка привязывается к пилоту один раз.
3. **План и жизненный цикл.** Пилот хранит план из шести строго разрешённых финансовых полей и ориентировочную выборку R3. До старта нужны шесть условий готовности. Оптимистические версии expectedVersion защищают от одновременного редактирования. Переходы: draft → running → in_review → reviewed либо returned → running после resume. Другие переходы запрещены.
4. **Журнал доказательств.** Только дата периода и четыре агрегированных целых числа. Записи с idempotency key и fingerprint. Исходные числа не исправляются: ошибочное наблюдение отзывают, затем создают новую строку. До 12 активных периодов, уникальная активная дата, DB-checks и журнал аудита/outbox. Изменения допустимы только в running.
5. **Независимая приёмка и отчёт.** Владелец или менеджер, отличный от отправившего, сверяет SHA-256 слепка плана, условий и результатов. Можно вернуть на доработку или принять к обсуждению при достаточной выборке. Это не подтверждает причинность или оплату. Возвращаются русский отчёт и защищённый CSV.

## Закрытые маршруты

Префикс: /api/industry/v1.

- POST /auth/login; GET /auth/me; POST /auth/logout — существующие аккаунты.
- GET/POST /guest/requests; PATCH /guest/requests/:id — заявки.
- GET/POST /guest/pilots; GET /guest/pilots/:id — пилоты.
- PATCH /guest/pilots/:id/readiness; POST /guest/pilots/:id/start — готовность и запуск.
- POST /guest/pilots/:id/observations; POST /guest/pilots/:id/observations/:observationId/void — результаты и исправления.
- POST /guest/pilots/:id/submit; POST /guest/pilots/:id/review; POST /guest/pilots/:id/resume — независимая приёмка.
- GET /guest/pilots/:id/report; GET /guest/pilots/:id/report.csv — отчёт.

POST/PATCH при сессии требуют X-CSRF-Token из cookie. Для создания заявки или наблюдения требуется Idempotency-Key. Для переходов пилота — expectedVersion из последнего GET. Не выводите пароли, Cookie и CSRF в общие журналы.

## Рабочий кабинет

Адрес /assets/guest/console.html. Русскоязычный закрытый интерфейс использует только same-origin /api/industry/v1 с credentials: same-origin. Пароли и токены не сохраняются в localStorage. Есть понятный режим отсутствия API, отображение заявок, квалификация, создание пилота, условия, запись/отзыв периодов, независимая приёмка и экспорт CSV.

**Важно:** публикация HTML не означает запуск защищённого сервера. Статический workflow deploy.yml синхронизирует только index.html и assets/**; он не устанавливает PostgreSQL, Docker compose, миграции и Nginx. До отдельной проверки инфраструктуры это кабинет, у которого API может быть недоступен.

## Независимая приёмка

CI .github/workflows/industry-api-ci.yml запускает PostgreSQL 16, отдельную минимально привилегированную industry_app без BYPASSRLS, повторно применяет миграции и выполняет npm test, включая test/guest.test.mjs. Проверяется:

- отказ анонимам и при отсутствии CSRF;
- запрет доступа к другим компаниям на уровне API и DB RLS;
- роли, схемы полей, версии и переходы статусов;
- идемпотентные параллельные записи, отзыв/повторный ввод;
- SHA слепка, запрет самостоятельной приёмки, достаточная выборка;
- аудит/outbox и CSV, не раскрывающий учётные записи.

CI .github/workflows/guest-experiment.yml проверяет статические контракты, CSP, Node и Chromium desktop/mobile. Визуальные проверки кабинета подменяют ответы HTTP для тестирования UX — не являются проверкой базы данных. Обе CI должны быть зелёными.

## Перед реальной эксплуатацией

1. Подтвердить законность данных и коммуникаций, назначить ответственного за безопасность, обеспечить сроки хранения. Названия заявок свободные текстовые поля: нельзя вписывать имена, телефоны и другие личные данные; техническая проверка не умеет выявлять личные сведения внутри названия.
2. Обеспечить зашифрованный бэкап PostgreSQL и независимое восстановление, ротацию ключей, управление доступом и мониторинг. Никогда не загружать .env, пароли, ключи и архивы в GitHub или assets/.
3. По существующему регламенту Industry API развернуть compose.yml в отдельно согласованном production-окружении; provision ролей, миграция, bootstrap первого владельца, затем HTTPS reverse proxy к loopback API. Использовать DATABASE_URL с индустриальной ролью минимальных привилегий, не администраторской. Команда docker compose down -v удаляет данные — не использовать.
4. Проверить NODE_ENV=production, ALLOWED_ORIGIN=https://osmanx.world, TLS, cookies Secure/HttpOnly/SameSite Strict, CSRF, ограничения IP и rate limits Nginx. Не использовать демонстрационные логины.
5. После запуска API — тест двух разных компаний и двух сотрудников: отсутствие доступа между арендаторами, невозможность самоприёмки, соответствие контрольных сумм, неизменность одобренных данных. Отдельно проверить резервную копию и восстановление.
6. Только затем запускать реальный клиентский пилот. Stripe, RUB-платежи, налоговые регистрации, договоры и подписки в R4 не реализованы. Статус reviewed — **обсуждение**, не юридическая приёмка или оплата.

## Откат

Миграция 004 лишь добавляет таблицы и RLS-политики. При необходимости откатить API к предыдущему image, не удаляя новые таблицы; миграции версионируются через schema_migrations. Статические файлы откатываются revert-коммитом после проверки Deploy и HTTP. Резервное копирование и восстановление проверить до ввода реальных клиентов.
