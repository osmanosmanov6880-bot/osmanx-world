# OSMANX Guest Intelligence R9 — диагностические решения и импорт агрегатов

18 ноября 2026. Область: сервис Industry API, русский закрытый кабинет Guest и тестирование.

## Пять крупных блоков

### 1. Детерминированная диагностика, а не «магический AI»

src/guest-diagnostics.mjs получает только:
- замороженный R8-протокол, цель по размеру выборки, текущую фазу;
- агрегированные числа по контрольной и тестовой группам из проверенной tenant-схемы.

Правила показывают отсутствие данных, недостаточную выборку, перекос размеров групп более 20%, несостоявшуюся предрегистрацию, ручной источник, несистемное распределение, риск неполного покрытия периода и отрицательную наблюдаемую разницу. Каждое правило выдаёт код, важность, обоснование текущими агрегатами и проверяемый следующий шаг.

**Никаких гарантий причинного эффекта или выручки.** Система не видит реальные чеки, рекламу, персонал, платёжные поступления и не может «найти любую проблему».

### 2. Защищённый диагностический API

GET /api/industry/v1/guest/pilots/:id/diagnostics — авторизованный участник компании получает выводы только по своему пилоту. Ответ содержит версию пилота, контрольную сумму доказательств и объект osmanx.guest.diagnostic.v1. После изменения или отзыва периода диагностика пересчитывается из актуальной базы, не из кэша браузера.

### 3. Журнал управленческих действий

Миграция 008 создаёт guest_actions с FORCE RLS, уникальностью (tenant, pilot, code), ответственным сотрудником и датой. Владелец/управляющий выбирает только реально предложенный диагностикой код, действующего сотрудника своей организации с правом работы и срок до 180 дней. Оператор может изменять лишь назначенные ему задачи; viewer — читать.

Маршруты:
- GET /guest/pilots/:id/actions — журнал задач.
- POST /guest/pilots/:id/actions — JSON {expectedPilotVersion,code,assigneeId,dueDate}.
- PATCH /guest/pilots/:id/actions/:actionId — JSON {expectedVersion,status}.

Разрешённые переходы: open → in_progress → done или open/in_progress → dismissed. Завершённые задачи невозможно переоткрыть через API. Каждое изменение входит в audit_events/outbox. Никаких свободных комментариев и контактов гостей.

### 4. Атомарный импорт обезличенных CSV

Формат строго один:

    date,control,controlReturn,offer,offerReturn
    2026-11-09,900,180,700,210
    2026-11-10,900,180,700,210

До 4 КБ и 12 ISO-дней; только целые числа без формул, кавычек, имён, телефонов, email или дополнительных полей. Даты должны быть в зафиксированном протоколе и не в будущем. Сравнение с активными периодами предотвращает повторную запись.

- POST /guest/pilots/:id/observations/import/preview — JSON {expectedVersion,csv}; только проверка, возвращает SHA-256 и сводку.
- POST /guest/pilots/:id/observations/import — JSON {expectedVersion,csv,sha256} + заголовок Idempotency-Key. Сервер сам пересчитывает SHA-256, блокирует версию пилота, проверяет даты и занятые периоды. Транзакция записывает всё или ничего, с одной новой версией и записью в guest_bulk_imports.
- GET /guest/pilots/:id/observations/imports — журнал успешных партий без сырого CSV.

Повтор с одинаковым ключом и пакетом возвращает ранее принятую партию, не дублируя наблюдения. Исправления выполняются только через контролируемое аннулирование периода и запись нового.

### 5. Русский кабинет и сквозные тесты

Кабинет R9 добавляет:
- рекомендации с явными причинами и приоритетами;
- назначение сотрудника, срока, статуса задачи;
- файл CSV, предпросмотр, контрольную сумму и явное подтверждение;
- same-origin cookies + CSRF, без localStorage/sessionStorage и без ложного успешного сохранения.

Проверка: PostgreSQL 16, роли owner/manager/operator/viewer, RLS двух компаний, SHA-256, replay, конфликт импорта параллельных отправителей, аудиторские события, Chromium desktop/mobile, восстановление старого evidence.v1 вместе с двумя новыми R9-журналами через два разных age-ключа.

## Условия развёртывания

1. Внедрение migration 008 — только после бэкапа и под контролем оператора. /health/ready должен вернуть version 008, FORCE RLS на семи Guest-таблицах и отсутствие лишних SQL-привилегий. Старые архивы и доказательства v1 остаются читаемыми.
2. GUEST_WRITES_ENABLED=false до настоящей двухсотрудниковой приёмки в staging. Пользователь VPS deploy-osmanx не имеет прав на Docker/PostgreSQL/Nginx; публикация статики НЕ означает запуск API.
3. Обрабатывать только законные обезличенные агрегаты. Законность коммуникаций, источники, выборку, независимость групп и согласия владелец проверяет отдельно.
4. Stripe, VAT, реальные счета, рублёвые оплаты, подписки и подтверждённая выручка в R9 не включены.
5. Откат клиентской статики — revert PR. Откат API — предыдущий проверенный образ без удаления БД; не выполнять docker compose down -v.
