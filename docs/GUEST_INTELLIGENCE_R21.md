# OSMANX Guest Intelligence R21 — независимый аудит инфраструктуры и проверяемый пакет готовности

19 ноября 2026. Отдельный **draft PR поверх R20 #54**. Дополнительные зависимости: R19 #53, R18 #52, R17 #51, R16 #49, R15 #48, R14 #47. Вся цепочка ещё не слита. Действующий main, сайт osmanx.world, VPS и клиентская база этим выпуском не затронуты.

## Пять инженерных реализаций

1. **Седьмой этап проверяемого дерева релизов.** `scripts/r21-release-chain.mjs --github`: только GitHub GET, фиксированные PR #47/#48/#49/#51/#52/#53/#54 и 40-символьные SHA, проверка точных требуемых CI jobs и наследования коммитов через GitHub compare API. Отчёт отдельно показывает корректную сборку в незавершённых PR и факт настоящего слияния. Никогда не вызывает merge/deploy/enable writes.
2. **Локальный VPS postural audit.** `scripts/r21-host-posture.mjs --local`: read-only проверка Linux/Node, разрешённого Origin, отключённых Guest writes, приватных файлов независимых операторов, каталогов вне checkout, прав и отсутствия симлинков, слушателя canary только на 127.0.0.1:3150 и PostgreSQL, не открытого наружу. Анализирует `ss -ltnH`, не раскрывает пароли, ключи, имена файлов/пользователей, внешние адреса и содержимое ключей. Если команда `ss` недоступна, нет владельца проверки, отсутствует независимое подтверждение или нет доверенного файла — NO-GO. Скрипт надо запускать **физически на разрешённом VPS**: успешный CI не является аудитом реального сервера.
3. **Read-only PostgreSQL security and retention audit.** `src/guest-r21-db-audit.mjs` и `scripts/r21-db-audit.mjs` сверяют миграции 011–014, FORCE RLS пяти таблиц, статус не superuser/BYPASSRLS, запрет UPDATE/DELETE журналов, контрольные точки R17/R18, расход дневной квоты и количество неизменяемых событий, превышение допустимого хранения. Только SELECT, отдельная транзакция `BEGIN READ ONLY` и последующий `ROLLBACK`. Требуется loopback PostgreSQL и tenant/pilot UUID. Сбор личных данных, очистка и миграции не производятся.
4. **Доказательный, но НЕ разрешающий пакет.** `scripts/r21-evidence-bundle.mjs` и `scripts/r21-assemble.mjs` объединяют ровно пять независимых private JSON отчётов (GitHub chain, host, database, isolated DR, two-person change-ticket), связывают их с конкретным tenant/pilot, полным SHA релиза, SHA подписанного R19 scope и временем действия один час. Только ограниченный набор safe-полей, без закрытых ключей, email, URL подключения, записей клиентов и текстов документов. SHA-256 обнаруживает случайные изменения, но **не заменяет Ed25519 подписей R20** или внешнего WORM. Вывод создаётся новым файлом 0600 вне исходного checkout, без перезаписи или облачной передачи. Отчёт с NO-GO тоже полезен для аудита.
5. **Русский read-only кабинет и интеграционные CI.** В интерфейсе появился R21 экран, а в API — `GET /api/industry/v1/guest/pilots/:id/r21/posture`, доступный только владельцу/управляющему своей компании. Выводит причины ошибок RLS, grant, миграций, контрольных точек, событий и срока хранения; юридический допуск, реальный host и offsite/WORM всегда остаются внешними задачами. Автотесты охватывают два tenant, отказ после STOP, изменённую цепочку коммитов, публичный PostgreSQL, неправильные права, несоответствие дневной квоты, изменённый JSON, перепутанный tenant и истечение отчёта. Сохраняется полный набор R7–R20 и двухключевое AGE восстановление.

## Операторские команды — все read-only, на разрешённой машине

Из `services/industry-api`:

    node scripts/r21-release-chain.mjs --github
    node scripts/r21-host-posture.mjs --local
    R21_AUDIT_DB_URL='postgresql://READ_ONLY_USER:...@127.0.0.1:5432/APPROVED_DB' \
      node scripts/r21-db-audit.mjs --tenant TENANT_UUID --pilot PILOT_UUID --retention-days 30

Токены/пароли/URL подключения не помещать в общедоступные журналы, issue или PR. `host-posture` никогда не превращается в разрешение производства: поле `independentOperatorConfirmed` по умолчанию false, пока независимый оператор не оформит отдельный внешний акт проверки.

Сначала независимо выполните R18 portable proof verify, R20 DR cross-check на отдельной восстановленной базе и R20 независимую проверку двухподписного change ticket. Результаты должны существовать как отдельные private 0600 JSON; перед публикацией проверяется их истинность, а не только форма.

Чтобы создать новый безопасный R21 отчёт (в порядке аргументов):

    node scripts/r21-assemble.mjs TENANT_UUID PILOT_UUID \
      FULL_GIT_SHA R19_SCOPE_SHA \
      /private/chain.json /private/host.json /private/database.json \
      /private/restore.json /private/ticket.json /private/r21-evidence.json

Команда читает ровно пять входов, проверяет ограничения, удаляет потенциально чувствительные лишние поля, добавляет SHA-256 и пишет новый результат без перезаписи. Текст `safeIsolatedRehearsal:true` в неподписанном JSON не может доказать факт внешней проверки; это лишь связанный технический вывод, требующий независимых источников и подписей. Архив **не загружается** в внешний WORM автоматически.

## Строгие условия до реального клиента

1. Все PR R14–R21 прошли независимый код-ревью, контролируемое слияние по порядку и новые CI на итоговой ветке main (не только в draft).
2. Отдельный уполномоченный оператор подтвердил фактическую конфигурацию VPS, резервное хранение двух AGE ключей, восстановление, публичный HTTPS и привилегии БД.
3. Юрист или уполномоченное лицо подтвердил реальный договор, законное основание обработки, жизненный цикл согласий, минимизацию данных, сроки хранения и правила уничтожения.
4. Независимый хранитель подписал R18 доказательства, R19 содержит допуск **одной** компании и пилота, R20 Change Ticket подписан двумя другими людьми; действуют R12/R13/R16/STOP механизмы.
5. Отдельное окно изменений согласовано человеком и испытано восстановление из зашифрованной внешней копии; только после этого возможен отдельный production rollout.

**Важное ограничение:** успешная программа, зелёные CI, SHA файла и даже положительный технический пакет **не дают** автоматической санкции на сбор реальных клиентских данных. Пакет R21 не содержит кнопок «разрешить», изменить БД или включить worker/платежи. Все сценарии CI выполняются исключительно с синтетическими UUID/данными.
