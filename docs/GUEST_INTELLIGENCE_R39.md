## Пять реализованных инженерных задач

### 1. Last-line-of-defense для прямого восстановления PostgreSQL

Исправление находится **внутри самого** `ops/restore-dr.sh`: теперь оператор не может обойти проверки запуска R36/R37 просто вызвав `sh ops/restore-dr.sh archive.age`. Обязателен локальный URL `postgresql://...` к `127.0.0.1`, `localhost` или `::1`, имя вида `industry_dr_*` без `live/prod/main`, без параметров URL или произвольного порта. Read-only `scripts/r39-dr-preflight.mjs` подключается к *реальному* PostgreSQL и проверяет имя базы, петлевой IP, порт, статус сервера, **отсутствие отношений в любой пользовательской схеме** (в том числе `public`) и отсутствие других сеансов. Данные доступа не попадают в ответ.

Скрипт проверяет это **до дешифрования** и **повторно перед SQL DDL**. Он отказывается от симлинков архива, .sha256 и файла AGE-ключа. Не запускается на рабочем сервере автоматически, новых прав на производство не выдаёт. В CI предусмотрена собственная отдельная PostgreSQL база с существующей `public`-таблицей: запуск обязан отказать.

### 2. Транзакционное AGE/pg_restore

`ops/restore-dr.sh` выполняет `pg_restore --single-transaction --exit-on-error --no-owner --no-acl` без параллельных workers. При ошибке SQL dump откатывается одной транзакцией. После восстановления проверяется наличие **не менее 11** миграций. Перед импортом может создаваться `btree_gist` extension в одноразовой базе (это отдельный предварительный DDL, вне транзакции pg_restore); поэтому неверно обещать, что **абсолютно все** операции откатятся при сбое. Нельзя применять этот скрипт к production.

### 3. Фактические privilege/mount границы Docker Compose

`src/guest-r39-compose-boundaries.mjs` подключён прямо к `scripts/r38-check-compose.mjs`: проверяет уже **подставленный** `docker compose config --format json`, без вывода секретов. Запрещает host-mode, privileged, cap_add, devices, дополнительные тома runtime-сервисов и docker.sock, небезопасные `read_only/tmpfs/init`, снимаемые setup-профили и запись в дополнительные host-монты. Допускается лишь named DB volume и точный read-only provision script. R14 supervision вызывает полный валидатор до операционного запуска. Локальные Docker-команды сами по себе не дают независимой аттестации удалённого VPS.

### 4. Действительный review packet по PR #47

`src/guest-r39-review-packet.mjs` и `scripts/r39-first-pr-review.mjs` читают GitHub **только GET**. Привязка к точному `840bb083e606058a9a32450f3b3a3e881a34891e`, всем **10 изменённым файлам**, Git tree и SHA-256 полного доступного patch каждого файла. Проверяется ожидаемый набор файлов R14. Пакет формирует предметные задачи ревьюеру: Docker Compose, shell canary, Ed25519 admission, read-only мониторинг, инциденты и привилегии GitHub Actions.

```bash

```

Если PR #47 меняется, проверка откажет и потребует новое ревью/перепривязку. Автоматического code review, approve или merge нет. Текущее исходное состояние #47: Draft без независимого GitHub approval. Последовательные PR 48–74 не считаются опубликованными.

### 5. Короткий офлайн-пакет оператора, тесты и повторная приёмка

`src/guest-r39-operator-handoff.mjs`, `scripts/r39-operator-handoff.mjs --stdin`. Из уже собранных отчётов формирует 7 конкретных дальнейших действий; сообщает, что было проверено локально, а что ещё нет. Принимает не больше 128 KiB JSON и **не выполняет ни сети, ни Docker, ни AGE, ни GitHub**. Его SHA фиксирует содержимое, но не является независимым подтверждением честности источников.

CI: `r39-offline`, `r39-postgres`, `r39-encrypted-dr`, `r39-reproducible`, `r39-release-graph`. Наследуется полный набор прежних тестов Fastify, PostgreSQL и tenant isolation.

- Внешне засвидетельствованные deployed staging version, приватность и RLS, восстановление двух независимых архивов, safe rollback и SLO.
