# OSMANX Guest Intelligence R5 — проверяемый запуск и двухсотрудниковый пилот

18 ноября 2026. PR #37. Кабинет: /assets/guest/console.html.
Приглашения: /assets/guest/join.html.

## Пять полноценных инженерных блоков

1. **Самодостаточный Docker runtime.** R4 API импортировал файлы из ../../../assets/guest, отсутствующие внутри Docker-образа. R5 включает точные одобренные версии математических модулей в services/industry-api/shared. Импорт теперь из ../shared. Оба CI проверяют их побайтное совпадение с публичными моделями, Docker CI импортирует реальные модули внутри образа.

2. **Второй сотрудник.** В кабинете владелец или управляющий может пригласить сотрудника через существующий API /staff/invitations. Одноразовый 256-битный токен показывается один раз, не включается в ссылку и не сохраняется в браузерном хранилище. Страница join.html принимает токен и пароль через /staff/invitations/accept. Управляющий не может приглашать управляющего. Владелец может отозвать приглашение и доступ сотрудника. Код компании сообщается адресату отдельно.

3. **Проверяемый архив.** Аддитивная миграция 005 расширяет guest_pilots архивными полями с SQL-check согласованности. GET /guest/pilots/:id/evidence.json возвращает канонический слепок агрегированных наблюдений, SHA-256, решение второго сотрудника и пояснение ограничений. Браузер пересчитывает SHA-256 через Web Crypto перед скачиванием. POST /guest/pilots/:id/archive доступен только владельцу, только после независимой приёмки и сверки доказательств. Исходные наблюдения и история проверок не удаляются. SHA-256 — проверка целостности, не внешняя криптографическая подпись.

4. **Read-only VPS и публичная проверка.** Расширен vps-readiness-inventory.yml: Docker, Compose, локальная доступность API, наличие конфигурации без чтения секретов, публичные статусы. Скрипт services/industry-api/scripts/guest-readiness.mjs независимо проверяет опубликованные HTML, /health/live, /health/ready и отказ 401 для защищённого маршрута. Публикация статики и работающий API — разные состояния. Проверки не изменяют инфраструктуру.

5. **Полный сквозной тест.** test/guest-r5.test.mjs использует PostgreSQL 16 и три независимые сессии: владелец, приглашённый управляющий, другая компания. Проверяет одноразовость приглашения, CSRF, RLS, заявку, готовность, наблюдения, запрет самоприёмки, независимое подтверждение, SHA-256 экспорта, owner-only архив, запрет изменений после архива и отзыв доступа без удаления истории. Chromium тестирует приглашение и присоединение в UI. Общие PostgreSQL тесты запускаются последовательно во избежание гонки за outbox.

## Доставка и эксплуатационная граница

Статический deploy.yml доставляет только index.html и assets. Проверяются SHA-256 на VPS и публичные маркеры console.html/js, join.html/js и предшествующих маршрутов. **Этот деплой не устанавливает API, PostgreSQL, миграции или nginx.**

Прежде чем включить реальную эксплуатацию:

1. Read-only inventory должен подтвердить Docker, Compose, отдельного ответственного за сервер и нужные права. Если deploy-osmanx может писать только в /var/www/osmanx.world, НЕ повышать его привилегии ради статического сайта. Запуск API должен выполнять отдельный уполномоченный оператор.
2. На проверенном сервере вне /var/www разместить services/industry-api, включая shared, scripts, migrations, ops и compose.yml. Персональные .env с правами 600, ключи age и резервные копии не хранить в GitHub, /assets и логах.
3. Перед миграциями обеспечить минимум два независимых age-ключа и успешное восстановление в изолированной среде. Не хранить оба приватных ключа рядом с зашифрованным архивом.
4. После проверки конфигурации на **точно установленном** сервере оператор выполняет команды из каталога сервиса:

       docker compose --file compose.yml config --quiet
       docker compose --file compose.yml up -d db
       docker compose --file compose.yml --profile setup run --rm provision
       docker compose --file compose.yml --profile setup run --rm migrate
       docker compose --file compose.yml --profile setup run --rm bootstrap
       docker compose --file compose.yml up -d api

   Это инструкция, а **не выполненные на VPS действия**. Миграция требует проверки целевой БД и подтверждённого бэкапа. Не выполнять docker compose down -v: это удаляет данные. Worker и внешние интеграции оставлять выключенными.
5. Добавлять ops/nginx-industry.conf в действующий HTTPS server block только после проверки администратором. Перед Nginx reload выполнить nginx -t. Docker API порт должен оставаться loopback 3047. Отдельно настроить HTTPS rate limiting.
6. Снаружи запустить node scripts/guest-readiness.mjs --require-api: ожидаются 200 для статики и health, 401 для закрытого списка пилотов. Затем в staging проверить вход двух разных сотрудников и всю цепочку от заявки до проверенного архива.

## Необходимые юридические и продуктовые ограничения

- Имена, телефоны гостей и другие личные сведения нельзя вписывать в поля свободного текста title и archive_reason; программный контроль длины не распознаёт всю персональную информацию.
- Отметка о проверке согласия не заменяет юридическую проверку фактического основания и условий обработки данных.
- Reviewed означает «принято к обсуждению», а не доказанный причинный эффект, подписанный акт, полученную выручку или оплату.
- JSON SHA-256 проверяет согласованность сохранённого слепка; независимую внешнюю подпись или абсолютную неизменяемость мы не заявляем.
- Stripe, налоги, рублёвые оплаты и автоматические подписки в R5 не подключены.
- Для отката UI сделать revert PR. Для отката API использовать предыдущий образ, не удаляя мигрированные таблицы и аудит; восстановление выполнять только из независимо проверенной копии.

## Приёмочные команды

Из services/industry-api:
- npm test
- npm run migrate (двукратно в PostgreSQL 16 с отдельно созданными ролями)
- docker build -t osmanx-industry-api:ci .
- docker run --rm --entrypoint node osmanx-industry-api:ci --input-type=module -e "await import('./src/guest.mjs')"
- node scripts/guest-readiness.mjs --report
- node scripts/guest-readiness.mjs --require-api

Если CI красный, PR не объединять. Если API недоступен, UI обязан показывать реальную ошибку, а не фиктивное сохранение.
