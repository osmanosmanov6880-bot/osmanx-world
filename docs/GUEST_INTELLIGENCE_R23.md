# OSMANX Guest Intelligence R23 — контролируемый план объединения, безопасная репетиция и передача оператору

19 ноября 2026 года. **R23 является отдельным draft PR поверх R22 #56.** Зависимости R14 #47 → R15 #48 → R16 #49 → R17 #51 → R18 #52 → R19 #53 → R20 #54 → R21 #55 → R22 #56. Реальные main, osmanx.world, VPS, клиентские записи и платёжные системы не меняются.

## Пять технически реализованных блоков

1. **Пошаговый human-only план для девяти PR.** `scripts/r23-merge-plan.mjs` проверяет SHA всех PR, требуемые успешные CI и GitHub ancestry; для R22 #56 отдельно проверяются пять точных CI и неизменность текущего main. Любое неожиданное изменение SHA, неподтверждённая mergeability, черновик и неслитый PR блокируют решение. Порядок и зафиксированные 40-символьные SHA выводятся в отчёте. Скрипт только GET и не содержит вызовов GitHub merge/close/rebase/dispatch или команд git push.
2. **Парный безопасный HTTP canary.** `scripts/r23-http-canary.mjs` запускает существующий строго ограниченный R14 монитор на двух точных origin: `http://127.0.0.1:3150` и `https://osmanx.world`. 10 GET без авторизации, cookies, редиректов и тела клиента проверяют /health/live, /health/ready и три неавторизованных маршрута. Проверяется строгая 401-приватность, готовность БД, RLS и что запись гостей отключена. Если production API не поднят, публичная проверка **должна** вернуть NO-GO; зелёный HTTPS сайта без API не приравнивается к работе API.
3. **Репетиция реальной межклиентской изоляции RLS.** `scripts/r23-tenant-isolation.mjs` требует два заранее созданных пилота разных компаний в тестовой или отдельно разрешённой среде и подключение к БД под непривилегированной API-ролью. Выполняет `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`, поочерёдно задаёт transaction-local tenant scope, доказывает видимость собственного UUID и отсутствие видимости чужого без явного tenant фильтра; в конце ROLLBACK. Подмена ID, видимость чужого пилота, BYPASSRLS или отсутствие одного контрольного пилота → блокировка. Данные и email в отчёт не экспортируются.
4. **Ограниченный операторский handoff.** `scripts/r23-operator-handoff.mjs` принимает пять отчётов: девяти-PR план, HTTP canary, реальный двухклиентский RLS, DR двух копий R22, предыдущий R22 preflight. Привязывает их к tenant/pilot, полному SHA и SHA действующего scope, проверяет все известные схемы, выводит только allowlist булевых проверок и машинные коды (email/ключи/пути отклоняет), считает SHA-256 и срок 30 минут. Выгрузка возможна только в новый приватный файл с правами 0600 вне исходного checkout; никакого автоматического переноса в WORM. SHA-256 не аутентифицирует оператора и не является юридическим согласием.
5. **Русский рабочий экран и E2E.** Новый read-only `/api/industry/v1/guest/pilots/:id/r23/handoff` доступен только владельцу/управляющему своей компании. Он показывает 16 проверок и семь шагов человеческой приёмки. Нет кнопок слияния, публикации, снятия STOP или включения сбора гостей. Автотесты проверяют неправильные SHA, origin, HTTP-редиректы, настоящую межклиентскую RLS, утечки, подпись/TTL пакета и запрещённые операции. Полный регрессионный тест включает R7–R22, Fastify/PostgreSQL и AGE DR.

## Безопасные операторские команды

В `services/industry-api`, если GitHub read-only токен предоставлен независимо:

    node scripts/r23-merge-plan.mjs --github

На проверяемом VPS при наличии разрешённого оператора — только анонимные GET:

    node scripts/r23-http-canary.mjs --compare

Эта команда возвращает код ошибки, если публичный API пока не подключён. `r23-tenant-isolation.mjs` экспортирует `rehearseR23TenantIsolation(pool,{tenantA,pilotA,tenantB,pilotB})`, а не готовую CLI команду на production: подключение и существование двух документированных контрольных пилотов предоставляются отдельно уполномоченным администратором. В CI эта проверка запускается с двумя **синтетическими** компаниями и отдельной временной PostgreSQL-базой.

`makeR23Handoff()` и `verifyR23Handoff()` экспортируются в `scripts/r23-operator-handoff.mjs` для офлайн-сборки отчёта из пяти отдельных источников. Даже если все checks технически положительны, поля `automaticMergeAllowed`, `customerGo`, `productionAuthorized` и `productionChanged` всегда `false`. Любое подозрение на изменение данных, срок или привязку к другой компании блокирует верификацию.

## Обязательные действия перед первым реальным клиентом

Нужно независимо рассмотреть и поочерёдно слить все PR R14–R23, выполнить полный CI уже на конечном main, проверить защищённую ветку и публичный HTTPS, провести физическую приёмку VPS и восстановление из внешних AGE/WORM копий, проверить договор, законное основание обработки, механизм отзыва/удаления данных, завершить двухоператорный change ticket и отдельно разрешить производственный rollout.

**Все эксперименты CI синтетические. Никакие зелёные тесты, пользовательский экран или хэш файла не доказывают реальные подписи/договоры или корректность настоящего VPS.**
