# OSMANX Guest Intelligence R34 — production launch blockers and operator tools

Дата: 20 ноября 2026. Основа: Draft R33 PR #68, HEAD `9957b916a3e72fbf7aba73d0e9da0f176013a037`. R34 создаётся новым stacked Draft, не изменяет `main` или действующий сайт.

## Пять полноценных блоков

### 1. Реестр 20 PR с конкретным следующим шагом

`src/guest-r34-source.mjs`, `scripts/r34-review-github.mjs --github`. Строго проверяются предыдущие 19 исходных PR, новый PR #68, pinned HEAD, пять поимённых CI, неизменность ветки, parent-коммит и деревья Git. `nextManualAction` указывает **первый ещё не объединённый PR и его точный SHA** для отдельного ручного ревью. Это read-only GitHub GET: не выполняется merge, push, approval, deploy или CI dispatch. Успешный source CI не является приёмкой итогового `main`.

### 2. Реальный staging: DNS, TLS, 10 защищённых GET

`src/guest-r34-host-evidence.mjs`, `scripts/r34-operator-staging.mjs`. Только после явного одобрения оператора проверяется **фиксированный** `staging.osmanx.world`. DNS IPv4 обязан быть публичным и стабильным; GET-запросы идут на проверенный и **закреплённый IP**, чтобы исключить rebinding; TLS с обязательной авторизацией CA и SNI. Из сертификата вычисляется SHA-256, DNS IPv4 сохраняется только в агрегированном SHA-256. Дважды с интервалом минимум 30 секунд запрашиваются пять неизменных маршрутов: health 200 и приватные guest endpoints 401. Сохраняются только код ответа и время; тела, cookies, клиентские данные и секреты не сохраняются. HTTPS-переадресации не следуются, хост production никогда не проверяется этим инструментом.

**Реальные запросы не выполняются автоматически в CI, из браузера или API.** Оператор должен самостоятельно подтвердить права на выделенный staging и его безопасную конфигурацию. Команда запуска на разрешённой staging-машине:

```bash
cd services/industry-api
GUEST_R34_OPERATOR_APPROVAL=APPROVED_READ_ONLY_STAGING \
  node scripts/r34-operator-staging.mjs --approved-staging PILOT_UUID EXACT_R33_GIT_TREE_SHA
```

Оператор обязан подставить настоящий UUID тестового пилота и 40-символьный SHA дерево R33, полученный из read-only проверки GitHub; выполненный GET не утверждает, что независимый эксперт засвидетельствовал настоящий VPS.

### 3. Две независимо зашифрованные offsite-копии и RTO/RPO

`src/guest-r34-custody.mjs`, `src/guest-r34-quorum.mjs`. Подтверждения `offsite_custodian` и `independent_recovery_auditor` должны использовать два разных pre-pinned публичных ключа Ed25519. Для копий A/B проверяются отличные archive SHA, fingerprints ключей, условные регионы, изолированные `industry_dr_r34_*`, совпадающие контрольные суммы и числа восстановленных строк, непротиворечивые времена и целевые RTO/RPO. **Это криптографическая проверка заявлений, а не автоматически выполненное восстановление.** Для реального результата требуются действия и независимые подписи внешних операторов, в том числе проверка доверия к ключам.

### 4. Подписанный ограниченный договорный допуск пилота

`src/guest-r34-client.mjs` требует двух разных подписантов `authorized_client` и `data_protection_reviewer`. Обязательны SHA-256 договора, DPA, уведомления, оценки законного основания и процедуры удаления. Допускается только заявленная обработка агрегированных показателей `aggregate-guest-metrics`, без идентификаторов, экспорта третьим сторонам и хранения более 30 дней. **Подписанные хеши не подтверждают юридическую действительность документов или полномочия конкретных физических лиц.** Продукт сохраняет `productionCollectionAuthorized:false`.

### 5. Операторский пакет, веб-кабинет, API и CI

`src/guest-r34-acceptance.mjs` связывает все четыре подписи, одну компанию/пилот, Git-дерево, staging-свидетельства, DR и правовые метаданные. При внутренне согласованных доказательствах `canSubmitToHumanAudit:true`, но без исключений `productionAuthorized:false` и `customerGo:false`.

Офлайн-инструмент читает пакет до 256 КиБ и отдельно закреплённые **публичные** ключи четырёх ролей из безопасного локального файла, не отправляет доказательства по сети:

```bash
cd services/industry-api
R34_TRUSTED_PUBLIC_KEYS_FILE=/absolute/operator/pinned-public-keys.json \
  node scripts/r34-offline-review.mjs --offline < /absolute/operator/redacted-evidence.json
```

Веб-API, только owner/manager и только в своей компании:
- `GET /api/industry/v1/guest/pilots/:id/r34/readiness`
- `GET /api/industry/v1/guest/pilots/:id/r34/report.csv`

Отчёт SHA-256 действует не более 10 минут и использует `Cache-Control: no-store`; CSV защищён от formula injection. Русский кабинет R34 всегда показывает NO-GO. Тесты проверяют 401 без сессии, 404 чужой компании, 200 owner/manager, отсутствие изменений в базе, STOP, ключи/подписи и недоступность записи. Пять CI jobs: `r34-offline`, `r34-postgres`, `r34-encrypted-dr`, `r34-reproducible`, `r34-release-graph`. Source manifest содержит `operatorReleaseReviewSupportedR34:true`, но `guestWritesDefault:false`.

## Оставшиеся обязательные внешние проверки

1. Отдельное человеческое code review и последовательный ручной merge 20 PR с повторной проверкой изменившихся SHA.
2. Новый CI на окончательном `main` **после** объединения.
3. Разрешённая настоящая staging/VPS-проверка, независимый свидетель DNS/TLS/HTTP и сверка происхождения пакета с работающим хостом.
4. Реальное offsite-восстановление, проверка доступа и физическая репетиция отката на безопасной среде.
5. Проверка подлинного договора, правового основания, роли клиента и санкционированного окна изменений.

Эти действия **ещё не выполнены** в R34. Никаких автоматических merge/deploy/migrate, реальных клиентских записей или снятия STOP. До завершения независимой эксплуатационной приёмки — **NO-GO**.
