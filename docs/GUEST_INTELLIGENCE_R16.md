# OSMANX Guest Intelligence R16 — мультиарендность, быстрый отзыв и независимый допуск

Дата: 19 ноября 2026. **Stacked-ветка поверх R15 PR #48, который зависит от R14 PR #47.** По умолчанию никаких включённых клиентских записей, платежей или деплоя на VPS.

## Пять полноценных компонентов

1. **Двухподписной реестр до 64 компаний.** Только подписанный операторским owner и manager Ed25519 файл registry.json, с полным SHA релиза, возрастающей revision, сроком не больше 12 часов, упорядоченным списком tenant UUID и списком отозванных компаний. Отдельный R15-пакет и R14-доказательства нужны каждой компании. Реестр НЕ хранит гостей и не выдаёт глобальные права.
2. **Моментальный отзыв.** Список revoked подписан двумя людьми; единственная запись может быть отключена, сохранив доступ другим компаниям. Для срочной остановки уполномоченный оператор может создать защищённый STOP-маркер для организации или всего реестра. API проверяет маркеры на каждом POST/PATCH/PUT/DELETE. Нет автоматического восстановления.
3. **Серверный tenant gate + безопасное отображение статуса.** Сервер получает tenant_id ТОЛЬКО из авторизованной сессии, проверяет его по подписанному реестру после входа и заново читает R14/R15 документы. Унаследованные R12, R13, CSRF и PostgreSQL RLS остаются обязательными. GET /api/industry/v1/guest/admission/self показывает только информацию своей организации сотруднику owner/manager. Русский кабинет отображает этот статус, не позволяя управлять подписями.
4. **Независимый инструментарий.** scripts/r16-operator.mjs для просмотра всего реестра и экстренной остановки, scripts/r16-signer.mjs для подписи owner и manager на РАЗНЫХ устройствах и итоговой проверки двумя публичными ключами. Ни один скрипт не разворачивает инфраструктуру, не снимает стоп и не включает сбор сам.
5. **Сквозные испытания.** Эфемерные синтетические ключи и документы, реальный Fastify/PostgreSQL с двумя компаниями, проверки чужого tenant, изменения подписанного реестра, устаревших версий, неправомерных подписей, блокировки и доступности исторического чтения. Также Node-тест русского кабинета и CI.

## Частная файловая структура для будущего разрешённого оператора

ВЫНЕСИ за пределы GitHub, /app и каталога сайта:

    /secure/osmanx-r16/
      registry.json                  # chmod 600, операторская двойная подпись
      platform-owner.pub.pem         # закреплённый публичный ключ
      platform-manager.pub.pem       # отдельный публичный ключ
      STOP                           # необязательный экстренный global hold
      tenants/
        00000000-0000-4000-8000-000000000001/
          admission.json            # полный R14 пакет, chmod 600
          permit.json               # подписанный R15 tenant пакет, chmod 600
          owner.pub.pem
          manager.pub.pem
          STOP                       # необязательный локальный hold

Все каталоги и файлы должны принадлежать уполномоченному администратору; registry.json, admission.json, permit.json — 600. Символьные ссылки и путь внутрь checkout отвергаются. Имя файла registry.json фиксировано. В подписанном индексе нет произвольных путей, SQL или информации гостей.

Для R16 в production нужны следующие переменные среды (в приватной конфигурации **вне** репозитория):

    GUEST_WRITES_ENABLED=true
    GUEST_RELEASE_COMMIT=<полный 40-символьный SHA проверенного релиза>
    GUEST_R16_REGISTRY_FILE=/secure/osmanx-r16/registry.json
    GUEST_R16_OWNER_PUBLIC_KEY=/secure/osmanx-r16/platform-owner.pub.pem
    GUEST_R16_MANAGER_PUBLIC_KEY=/secure/osmanx-r16/platform-manager.pub.pem
    GUEST_R16_MIN_REVISION=1

Важное правило: если хоть одна GUEST_R16_* переменная задана, но конфигурация неполная, сервер закрывает Guest-запись и НЕ переходит на R15. Для прошлого режима без R16-переменных действует старый одноклиентский R15 допуск.

## Формат подписанного registry.json

Упорядоченные ключи: schema, releaseCommit, revision, issuedAt, expiresAt, tenants, revoked, attestations. Пример полей для подготовки **unsigned** файла:

    {
      "schema": "osmanx.guest.r16.registry.v1",
      "releaseCommit": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "revision": 1,
      "issuedAt": "2026-11-19T08:00:00.000Z",
      "expiresAt": "2026-11-19T10:00:00.000Z",
      "tenants": [{"tenantId":"00000000-0000-4000-8000-000000000001"}],
      "revoked": []
    }

Указанные SHA и UUID — **фиктивные образцы**, а не настоящее разрешение. UUID внутри tenants строго отсортированы по возрастанию. revoked содержит объекты {tenantId,reasonCode,revokedAt}, где reasonCode — operator_request, security_incident, consent_withdrawn или contract_expired. Ключи в signed-файле формируются функцией registryMessage, включая ВСЮ версию, время, индекс и отзыв.

### Подписи на отдельных машинах

Владелец делает на собственной доверенной машине (не отправляя закрытый ключ):

    node scripts/r16-signer.mjs sign owner platform-owner-1 /private/unsigned.json /private/owner.key.pem /private/owner.part.json

Другой управляющий на другом устройстве:

    node scripts/r16-signer.mjs sign manager platform-manager-2 /private/unsigned.json /private/manager.key.pem /private/manager.part.json

После получения только раздельных signature-part файлов оператор проверяет и собирает результат:

    node scripts/r16-signer.mjs assemble /private/unsigned.json /private/owner.part.json /private/manager.part.json /private/owner.pub.pem /private/manager.pub.pem /private/registry.json

Ключи должны быть разными и независимо сохранёнными; private PEM не загружается в CI, GitHub, чат или веб-приложение. Скрипт assembler не перезаписывает существующий registry.json. Перед вводом подписанной новой версии оператор атомарно заменяет старый файл, сохраняет архив и поднимает установленную в защищённой среде минимальную revision.

**Откат реестра:** внутри работающего Node-процесса R16 запоминает максимальную подтверждённую revision и SHA. При повторном запуске этот барьер может быть потерян, поэтому GUEST_R16_MIN_REVISION — обязательная защищённая внешняя нижняя граница. После *каждого* отзыва или перевыпуска она должна быть повышена до новой revision до возобновления приёма. Иначе защита от отката после перезапуска не гарантирована. Нужны администраторское управление и журнал обновлений вне приложения.

### Экстренный стоп

Сначала read-only инспекция:

    node scripts/r16-operator.mjs review
    node scripts/r16-operator.mjs review-tenant TENANT_UUID
    node scripts/r16-operator.mjs review-canary

Только уполномоченный администратор, с явным подтверждением:

    R16_STOP_ACK=CONFIRM_R16_STOP_NO_RESUME node scripts/r16-operator.mjs stop-tenant TENANT_UUID
    R16_STOP_ACK=CONFIRM_R16_STOP_NO_RESUME node scripts/r16-operator.mjs stop-global

Экстренная блокировка не удаляет пилоты, журнал R13, PostgreSQL и архивы. Код не содержит API/CLI автоматического удаления STOP. Снятие допуска требует отдельной независимой процедуры у администратора и нового подписанного пакета. Не использовать docker compose down -v.

## Приёмка и GO/NO-GO

CI проверяет алгоритмы подписей и R7–R16 тесты на синтетическом PostgreSQL. Canary R14 (127.0.0.1:3150) всегда остаётся с GUEST_WRITES_ENABLED=false. До начала реального сбора должны быть также отдельно проверены полномочия VPS, offsite backup/restore реальной БД, правовые основания, согласия, договор, сроки хранения, два сотрудника, собственный R14/R15 допуск каждой компании и работающий канал реагирования. Даже зелёный CI **не** разрешает сбор клиентов автоматически.

Ограничение: STOP-файлы и офлайн-реестр защищены правами ОС и подписью, но не являются неизменяемым аппаратным журналом. При компрометации администратора сервера или защищённой нижней границы версии возможен откат; для масштабного коммерческого использования нужен внешний доверенный журнал, независимый мониторинг и отработанная процедура восстановления.
