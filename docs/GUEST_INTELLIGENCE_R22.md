# OSMANX Guest Intelligence R22 — независимая приёмка перед первым клиентом

Дата: 19 ноября 2026 г. Код R22 находится только в черновом PR поверх R21 #55. Зависимая цепочка: R14 #47 → R15 #48 → R16 #49 → R17 #51 → R18 #52 → R19 #53 → R20 #54 → R21 #55. **Ни одна из этих веток не является разрешением на production; главная ветка и рабочий VPS этим PR не меняются.**

## Пять инженерных блоков

1. **R14–R21: восьмиступенчатая релизная цепочка.** `scripts/r22-release-chain.mjs --github` читает только GET GitHub: восемь закреплённых PR, 40-символьные коммиты, точные CI-проверки, compare-ancestry. Дополнительно читает `/branches/main` и правила защиты ветки. Отсутствие доступа к branch-protection API, запрета force-push либо одобрения review не считается успехом: возвращаются коды блокировки. Никаких merge, workflow_dispatch, write permission или публикации.
2. **Независимо подписанное состояние VPS.** `scripts/r22-host-witness.mjs` формирует строго ограниченный набор технических признаков, не включая IP, приватные пути, имя оператора сервера, переменные окружения, закрытые ключи, пароли или пользовательские записи. Независимый офлайн-оператор создаёт Ed25519 подпись SHA-256 этого набора с привязкой к release SHA, tenant, pilot и сроком 30 минут. Проверка отказывает при повторном ключе R18/R19/R20, изменении портов, устаревшем свидетельстве или включённом сборе данных. Сам факт подписи НЕ доказывает физическую проверку настоящего VPS, поэтому требуется отдельный акт специалиста.
3. **Две независимые копии аварийного восстановления.** `scripts/r22-dr-quorum.mjs` получает два заранее восстановленных PostgreSQL `industry_dr_*` от независимых источников и ключей AGE. Сначала каждая база должна отдельно пройти прежнюю R20 проверку, затем в `BEGIN READ ONLY` сверяются R17/R18 checkpoint SHA, ревизии и номера журнала, R19 дневные квоты, сроки, SHA scope и количество append-only событий. Скрипт запрещает две ссылки на одну БД, одинаковый ciphertext SHA, одинаковый отпечаток публичного ключа получателя и одинаковое свидетельство внешнего хранения. Совпадение двух БД само по себе НЕ подтверждает, что две внешние WORM-копии физически существуют.
4. **Сквозная независимая оценка выпуска и защита отчётов.** `scripts/r22-preflight-review.mjs` объединяет исходные данные GitHub R22, проверяемую подпись VPS, подписанный R20 change-ticket, пакет R21, SQL-аудит и отчет двойного DR. Вновь проверяет точные tenant/pilot, SHA релиза, R19 scope и R18 anchor. При недостающих данных — NO-GO. При всех положительных технических полях — тоже нет автоматического `productionAuthorized`, `legalGo` или `customerGo`. Попутно усилен R21 evidence: внешние строки в полях ошибок теперь ограничены безопасными машинными кодами; email/URL/ключи/произвольный текст не копируются в секретно-безопасный отчёт.
5. **Русский кабинет первого пилота и сквозные испытания.** Новый read-only GET `/api/industry/v1/guest/pilots/:id/r22/launch-review` для владельца/управляющего только своей компании выводит отдельные локальные и внешние проверки. Переключателя production и команды снятия STOP нет. Автотесты проверяют GitHub lineage, неподтверждённые branch rules, Ed25519 и TTL, две DR-базы и подменённые квитанции, R21 evidence leak, полноценный HTTP/PostgreSQL маршрут и блокировку после STOP.

## Процедура для уполномоченного оператора

Проверка цепочки PR (только чтение, из `services/industry-api`):

    node scripts/r22-release-chain.mjs --github

Проверка настоящего VPS по-прежнему выполняется локально на машине уполномоченным человеком:

    node scripts/r21-host-posture.mjs --local

До подписания такого состояния независимый оператор обязан самостоятельно подтвердить, что данные собраны на проверяемом VPS, нет SSH/VPS или GitHub обхода, порты не выставлены публично, файлы доверия находятся вне кода и не изменились между проверкой и подписью. Произвольный JSON `gatheredOnHost:true` не служит подтверждением; криптографическая подпись лишь фиксирует ответственность и целостность предъявленных фактов.

Для двух DR-копий сначала независимо расшифруйте две разные копии с разными AGE ключами на отдельной офлайн-восстановительной машине, выполните `scripts/r20-restore-crosscheck.mjs` для каждой и документально подтвердите цепочки хранения. R22 `verifyR22DrQuorum()` проверит обе базы только в READ ONLY транзакциях. Двойной DR quorum не включает восстановление, удаление, миграцию или изменение LIVE PostgreSQL.

Для итогового отчёта вызовите `evaluateR22Readiness()` с отдельными подписанными доказательствами и фактическим GitHub snapshot. Возвращаемый результат документальный и остаётся NO-GO, даже если все локальные проверки зелёные. Реальный законный сбор данных разрешается только отдельным процессом уполномоченных лиц после полного закрытия зависимых PR, проверки актуального main и настоящей DR/WORM/юридической приёмки.

## Принципы безопасности

- Никогда не отправляйте приватные ключи, восстановленные клиентские данные, пароли и URL PostgreSQL в GitHub Actions или браузер.
- SHA-256 защищает от незамеченной модификации при доверенном исходном отпечатке, но не удостоверяет личность подписанта и не заменяет Ed25519.
- READ ONLY проверки не проверяют полноту самого бэкапа без сравнения с доверенной внешней контрольной точкой.
- Код R22 не имеет команды слияния PR, снятия аварийного STOP, переключения GUEST_WRITES_ENABLED, изменений Nginx/DNS, выдачи прав и отправки клиентской информации.
- Все CI проверки проводятся с синтетическими БД, ключами и отчётами. Успешный CI не подтверждает состояние реального VPS, наличие законного согласия и существование внешних WORM-копий.

## Что остаётся перед коммерческим production

Закрыть/слить PR R14→R22 в одобренное окно с независимым review, проверить итоговый main и публичный HTTPS, подтвердить реальные клиенты/правовые основания, подписанный документ первого пилота, опись операторов и ключей, две независимые DR-копии и внешний WORM retention lock. Только после успешной ручной процедуры возможен отдельный production change; этот PR такую операцию не выполняет.
