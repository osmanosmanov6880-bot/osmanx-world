# OSMANX Guest Intelligence R46 — полномасштабная репетиция слияния 32 PR и независимая приёмка

**20 ноября 2026.** Source: R45 Draft PR #94, `8dedf940900798c3ba726884fb952bc7ef397e4e`.

R46 предназначен **только для проверки и передачи на независимое ревью**. Не переводит Draft в Ready, не одобряет PR, не делает merge/rebase, не активирует customer writes и не изменяет production.

## Пять крупных блоков

1. **Полный закреплённый граф R14–R45 (32 PR):** `src/guest-r46-source-graph.mjs` проверяет актуальные 40-символьные SHA всех открытых PR, точные имена head/base и непрерывную последовательность; включает R45 #94. Повторно сверяет `main` в начале и конце чтения.
2. **Точная область ревью PR #47 относительно нового main:** `src/guest-r46-first-drift.mjs`, `scripts/r46-first-drift.mjs` вычисляют настоящий Git merge-base, точные десять допустимых файлов исходного PR #47, пересечение с изменёнными файлами `main` и критичные операционные области. Не читают и не публикуют секреты, содержимое файлов или клиентские данные. Нулевое пересечение НЕ доказывает безопасность слияния.
3. **32-ступенчатая виртуальная Git-репетиция:** `scripts/r46-virtual-merge.mjs` применяет `git merge-tree --write-tree --name-only --no-messages` к одному свежему `main` и ко всем 32 последующим pinned source-коммитам. На временном runner `git commit-tree` создаёт только недостижимые синтетические **Git-объекты** для следующего этапа. Не создаются ссылки веток, не выполняется `git merge`, `git rebase`, `git push` или изменение основного репозитория. При первом конфликте цепочка останавливается, сохраняются точный PR и конфликтующие пути. Контроль отпечатка всех локальных refs до/после обязателен.
4. **Два независимых доверенных человека и свежий CI каждого PR:** `src/guest-r46-reviewer-gate.mjs` отвергает автора, ботов, старые ревью на прежнем SHA, отозванные одобрения, активные `CHANGES_REQUESTED`, неполные страницы GitHub API и недоверенные учётные записи. Для подтверждения доверенных ревьюеров администратор явно задаёт `R46_TRUSTED_HUMANS` (через репозиторную переменную `GUEST_R46_TRUSTED_HUMANS`); отсутствие настройки = NO-GO. Проверяются 32 источника и их текущие GitHub Check Runs, а разрешение прочитать branch protection не приравнивается к доказательству соблюдения всех правил.
5. **GitHub Actions CI + операторский пакет:** отдельные unit/security test, настоящая одноразовая Git-репетиция и GET-only GitHub-отчёт для независимого ревью в JSON+Markdown. Все результаты проходят строгие схемы; CI может быть зелёным при существующих объективных бизнес/человеческих блокерах (проверяется *правильность диагностики*, не разрешение на публикацию).

## Воспроизведение

```bash
cd services/industry-api
npm ci --ignore-scripts --no-audit --no-fund
node --test test/guest-r43-acceptance.test.mjs test/guest-r44-acceptance.test.mjs test/guest-r45-acceptance.test.mjs test/guest-r46-acceptance.test.mjs
```

В **отдельном временном полном клоне**, где доступны все source SHA:

```bash
git fetch --no-tags origin main
node services/industry-api/scripts/r46-first-drift.mjs --json > first-drift.json
node services/industry-api/scripts/r46-virtual-merge.mjs --json > virtual-merge.json
node services/industry-api/scripts/r46-live-handoff.mjs --markdown first-drift.json virtual-merge.json > human-review.md
```

`r46-live-handoff.mjs` нужен `GITHUB_TOKEN` только с правами read для `contents`, `pull-requests`, `checks`. Настроить доверенных ревьюеров до использования их одобрений: `R46_TRUSTED_HUMANS=reviewer1,reviewer2`. Не заполнять вымышленными людьми: неизвестные личности оставляют статус NO-GO.

## Ручная последовательность приёмки

1. Человек-рецензент проверяет весь **PR #47** и изменившиеся с его ответвления файлы `main`. При необходимости сохраняет отдельно проверяемый reconciliation-коммит. Запрещено автоматически переписать 32 закреплённых SHA.
2. Проверяет все 32 зависимых PR, их обязательные source CI и два независимых доверенных одобрения на **актуальных SHA**.
3. Уполномоченный владелец проверяет branch protection и вручную объединяет PR строго в правильном порядке, если защита репозитория это разрешает.
4. После ручных объединений отдельно запускается **новый полный CI на новом main**: зелёный source branch CI этого не заменяет.
5. До реального signed/authorized staging, внешнего AGE/PostgreSQL restore, privacy/legal acceptance и отказоустойчивости **NO-GO**. `GUEST_WRITES_ENABLED=false`; STOP не снимается.

**Отсутствие технических конфликтов после 32 виртуальных шагов не является лицензией на слияние или разрешением на клиентские данные.** Все виртуальные объекты создаются только на одноразовом CI runner и не передаются в main.
