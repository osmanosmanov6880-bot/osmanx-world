# OSMANX Guest Intelligence R14 — безопасная эксплуатация

Дата: 18 ноября 2026. Исходный релиз: R13, коммит 7fab98a6.

## Пять инженерных блоков
1. Изолированный R14 canary: отдельные Docker-проект, PostgreSQL-том и сеть, API доступен **только** на 127.0.0.1:3150. Вебхуки/worker отсутствуют, GUEST_WRITES_ENABLED=false без возможности переопределить значением из .env.
2. Управляемый запуск: ops/r14-canary.sh plan/apply/health/stop; приватный .env только вне checkout, chmod 600, никакого remote Docker. Запуск требует явного подтверждения, не перезаписывает существующую БД, при непрохождении проверок останавливает API, но сохраняет том для расследования.
3. Мониторинг: scripts/r14-monitor.mjs выполняет пять анонимных GET; проверяет live, ready, migration 011, FORCE RLS, least privilege и 401 на защищённых маршрутах, включая safety. Никаких cookie, токенов, редиректов и POST.
4. Проверяемый допуск: scripts/r14-admission.mjs требует 11 свежих операционных и юридических доказательств, SHA-256 каждого артефакта, 40-символьный git SHA и две независимые Ed25519-подписи owner и manager. Решение привязано к точному набору доказательств; срок действия ограничен. **Положительный отчёт не включает запись и не заменяет фактическую юридическую проверку**.
5. Жизненный цикл сбоя: scripts/r14-incident.mjs переводит статус в incident после 3 последовательных отказов; требует 2 успешные проверки для снятия; не перезапускает инфраструктуру и не отменяет R13 hold без участия руководителей.

## Запуск на разрешённом локальном VPS только после отдельной подготовки

Не копировать сюда .env/пароли/ключи. Изолированный .env содержит поля из ops/.env.example с ключами age от независимых операторов. Не используйте данные клиентов в canary.

~~~bash
cd services/industry-api
bash ops/r14-canary.sh plan /absolute/private/r14.env
R14_CANARY_ACK=CONFIRM_ISOLATED_R14_NO_CUSTOMERS bash ops/r14-canary.sh apply /absolute/private/r14.env
bash ops/r14-canary.sh health /absolute/private/r14.env
R14_CANARY_ACK=CONFIRM_ISOLATED_R14_NO_CUSTOMERS bash ops/r14-canary.sh stop /absolute/private/r14.env
~~~

Отдельно запуск проверки мониторинга: \`node scripts/r14-monitor.mjs --local\` либо \`--public\`. Public-режим проверяет действующий домен, но не разворачивает API. Результат incident state-machine зависит от последовательности отчётов и должен обрабатываться операторским мониторинговым процессом, например cron/агентом. Этот релиз **не устанавливает** такой процесс на VPS.

## Формат заключения о допуске

Решение JSON schema \`osmanx.guest.r14.admission.v1\` с полями:
\`releaseCommit\` (полный 40-символьный SHA), \`evidence\` (точно 11 ключей, каждый \`{ok:true,sha256,observedAt}\`), \`attestations\` (ровно owner + manager). Записи подписываются Ed25519 по точным UTF-8 байтам JSON, возвращаемым функцией \`attestationMessage\`. Подписываются \`role\`, \`actorId\`, \`releaseCommit\`, \`evidenceDigest\`, \`acceptedAt\`, \`expiresAt\`. Публичные ключи двух сотрудников находятся за пределами репозитория. Частные ключи никогда не отправлять в GitHub.

~~~bash
node scripts/r14-admission.mjs /private/decision.json /private/owner.pub.pem /private/manager.pub.pem --require-go
~~~

Содержимое evidence sha256 должно ссылаться на реальные проверяемые акты: staging, RLS, мониторинг, учения остановки, offsite-restore, правовое основание, договор обработки, уведомление, сроки удаления, согласия, клиентский протокол. Код проверяет целостность и свежесть отметок, **не может автоматически установить достоверность самого документа или правомерность обработки**. Требуется независимое человеческое подтверждение.

## GO/NO-GO

R14 CI подтверждает реализацию кода, но не подтверждает развёртывание на VPS. Изолированный canary **не** равен production. Запрет на реальные данные остаётся, пока VPS-оператор не проверит независимый восстановленный бэкап, защиту API, согласия и юридическое основание, политику удаления, мониторинг и решение двух сотрудников. Публичный сайт не перенастраивается. Не использовать \`docker compose down -v\`.

Порядок аварийного реагирования: заморозить ввод клиентов; проверить R13 safety hold; изолировать неисправный API, не удаляя PostgreSQL; сохранить audit и зашифрованные архивы; восстановить в независимом окружении; получить новое решение owner/manager. Никакого автоматического снятия паузы при возвращении HTTP 200.
