# OSMANX Guest Intelligence R38 — исправления реальных проверок допуска

Дата: 20 ноября 2026. Основа R37 Draft PR #72, pinned SHA `a9f6cb0b7a9c6af6d005b5a634a1c277b42e8d5f`. R38 — отдельный stacked Draft, без изменений `main` или production.

## Пять больших инженерных задач

### 1. Проверка **итогового** Docker Compose, а не только исходного YAML
`src/guest-r38-compose-runtime.mjs`, `scripts/r38-check-compose.mjs`, подключено в `ops/r14-canary.sh` после R37 статической проверки и перед любыми `up/stop`. Вывод `docker compose config --format json` содержит уже подставленные значения, поэтому JSON **не логируется**. Проверяются ровно разрешённые сервисы `db/provision/migrate/bootstrap/api`, одна network `r14_private`, одна привязка API `127.0.0.1:3150:3047`, запрет опубликованных портов остальных сервисов, `GUEST_WRITES_ENABLED=false`, read-only и отсутствие повышенных привилегий. Отсутствующий, изменённый или опасный параметр блокирует canary. Важное ограничение: конфигурация на диске и реальные правила сетевой инфраструктуры — разные факты; второй требует проверки на хосте.

### 2. Исправление PostgreSQL DR: схема public тоже не должна содержать таблицы
`src/guest-r38-dr-safety.mjs`, подключено в `src/guest-r37-dr-verified.mjs` и операторский `scripts/r37-local-dr.mjs`. R37 проверял `industry` и «чужие» схемы, но мог пропустить пользовательские таблицы `public`. Теперь preflight подсчитывает `pg_class` в **любой пользовательской схеме**, включая `public`; отклоняет непустую базу. После AGE/pg_restore перепроверяет фактические relations, количество миграций, имя локальной БД, IP, порт и метку запуска сервера. Переключение на иной PostgreSQL экземпляр между проверками запрещено. Создание/удаление БД отсутствует.

### 3. Строгая оценка ревью текущего коммита
`src/guest-r38-review-policy.mjs` и живой read-only `scripts/r38-github-review.mjs`. Накопленная цепочка теперь 24 PR до R37 #72. Для первого ожидающего #47 проверяются полный набор страниц GitHub Reviews и checks, актуальный SHA, выход из Draft, последний отзыв каждого независимого логина и отсутствие активных `CHANGES_REQUESTED`. Старое `APPROVED` не перебивает новое изменение; устаревший SHA не засчитывается. Инструмент не делает merge или approve.

```bash
cd services/industry-api
node scripts/r38-github-review.mjs --github
```

### 4. Сводный пакет независимого оператора
`src/guest-r38-rollout-evidence.mjs` связывает отдельные доказательства Compose, восстановления, идентичности Docker образа и ревью PR. Даже при полностью успешных **локальных** проверках `customerGo=false` и `productionAuthorized=false`. Внешний staging, оффсайт-восстановление и юридический допуск проверяются отдельно. Хеширование пакета не превращает непроверенные подписанные заявления в доказательство.

### 5. Русский кабинет, tenant MANAGE API, CSV, end-to-end тесты
`src/guest-r38-report.mjs` + два защищённых пути:
- `GET /api/industry/v1/guest/pilots/:id/r38/readiness`
- `GET /api/industry/v1/guest/pilots/:id/r38/report.csv`

SHA-256, TTL до 10 минут, `Cache-Control: no-store`, CSV без пользовательских формул, явные причины NO-GO. Веб-процесс никогда не вызывает Docker/AGE/GitHub. Пять GitHub Actions jobs `r38-offline`, `r38-postgres`, `r38-encrypted-dr`, `r38-reproducible`, `r38-release-graph`; весь предыдущий набор R7–R37 сохранён.
