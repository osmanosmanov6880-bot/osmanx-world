# R7 — безопасный повтор отправки и поиск контактов

## Миграция

Применить `0006_r7_command_requests.sql` после миграций R1–R6. Она добавляет таблицу квитанций `command_requests` и индекс контактов по результату/дню. Существующие записи не изменяются, демонстрационные данные не добавляются.

## Повтор после обрыва связи

`POST /moscow-1000/api/command/contacts` и `POST /moscow-1000/api/command/expenses` принимают заголовок `Idempotency-Key`: 16–128 символов из `A–Z`, `a–z`, `0–9`, `.`, `_`, `:`, `-`. UUID подходит. Клиент создаёт ключ один раз для новой отправки и сохраняет **ту же пару нормализованных полей и ключа**, если результат отправки неизвестен. Самостоятельная генерация нового ключа при повторе создаст новую операцию.

Ответы:

- `201`, `idempotency_replayed:false`: новая запись сохранена.
- `200`, `idempotency_replayed:true`: эта операция уже была выполнена. Ответ содержит текущую запись с тем же ID; если её позднее отредактировали, возвращается актуальная ревизия. Повтор не восстанавливает старые значения.
- `409`, `code:idempotency_conflict`: такой ключ уже использован с другими полями. Сервер ничего не изменяет.
- `410`, `code:idempotency_target_removed`: запись ранее сохранили и затем удалили. Старый черновик её не восстановит.
- `503`, `code:migration_required`: таблица квитанций недоступна; запрос не переходит к незащищённому созданию.

Ключ ограничен проверенным пользователем и типом операции. Google использует проверенный стабильный `sub` вместе с провайдером; существующий вход через Access использует email. В таблице хранятся хеши субъекта, ключа и нормализованного тела, ID записи и время. Контактные данные, заметки, сырые ключи и токены туда не записываются.

Резервирование ключа, создание записи, увеличение общей ревизии и событие аудита выполняются одной транзакцией D1. Условные записи связаны с уникальным ID попытки; параллельные запросы, которые оба не нашли квитанцию, не могут создать две записи. Ошибка аудита откатывает и запись, и квитанцию.

Квитанции сохраняются после удаления контакта или расхода. Автоматического удаления по TTL нет: оно позволило бы старому офлайн-черновику создать удалённую запись заново. Для небольшого штаба экспедиции это осознанная политика хранения. При переносе/очистке базы необходимо переносить/сохранять и эти квитанции; очистка таблицы сбрасывает защиту старых ключей.

Вызовы без заголовка остаются совместимыми с клиентом R6; защиту повторной отправки получает клиент R7, передающий ключ. PATCH контакта по-прежнему требует `expectedRevision` и отклоняет устаревшие изменения.

## Поиск и следующий шаг

`GET /moscow-1000/api/command/contacts` принимает:

| Параметр | Значение |
|---|---|
| `day` | День 1–10, отсутствие — все дни |
| `q` | До 120 символов; поиск по названию, категории, человеку, каналу, проблеме и следующему шагу |
| `outcome` | `all`, `visited`, `dialogue`, `interest`, `refusal`, `meeting`, `pilot`, `contract` |
| `followup` | `all`, `pending`, `none` |
| `offset` | Смещение среди подходящих записей, 0–10000 |

`pending` означает непустой следующий шаг у записи, результат которой не `refusal` и не `contract`. Это список действий, **не календарь просроченных встреч**. `none` — дополнение этого множества. Все фильтры применяются одновременно.

Поиск не учитывает регистр русской кириллицы (включая Ё) и латиницы ASCII. `%` и `_` ищутся буквально, а не как SQL-шаблоны. Для других алфавитов полное Unicode-сопоставление регистра не заявляется. Все значения передаются SQL-параметрами.

Ответ содержит `contacts` (до 25 записей), `nextOffset` и `total` — число всех подходящих контактов. Получение страницы и количества происходит в одном читающем пакете D1. Публичный зрительский API не получает доступ к поиску или исходным контактам.

## Состояние Google-входа

`GET /moscow-1000/api/auth/config` сохраняет `configured` и `googleEnabled`, добавляя:

```json
{
  "setup": {
    "status": "needs_configuration",
    "callbackUrl": "https://your-origin.example/moscow-1000/api/auth/google/callback",
    "checks": {
      "googleClient": false,
      "sessionSecret": true,
      "adminAllowlist": true,
      "database": true
    },
    "missing": ["googleClient"]
  }
}
```

URL вычисляется из проверенного HTTPS-origin конкретного развёртывания. Статусы: `ready`, `needs_configuration`, `needs_migration`. Диагностика сообщает булевы результаты, не раскрывая client ID, секреты или список разрешённых email. Она не создаёт сессию и не подтверждает успешный вход в настоящий Google-аккаунт. `ready` означает готовность локальной конфигурации и таблиц; успешный внешний OAuth-обмен проверяется отдельным реальным входом.
